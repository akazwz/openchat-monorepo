## Design principles

- Only Astryx components and Astryx's official theme mechanism style the app. No StyleX in app code (no `stylex.create`/`props`/`keyframes`, no `xstyle`, no `@stylexjs/stylex` or `tokens.stylex` imports) and no custom CSS (no hand-written rules, `className`, or `style` for components); this overrides the generated block's "xstyle / StyleX tokens" rule above. Oxlint enforces it: importing `@stylexjs/*` or a `*.stylex` module fails `pnpm check` (`no-restricted-imports` in .oxlintrc.json), and the app does not depend on StyleX itself (Astryx brings it as its own peer). A visual adjustment is a component prop, a purpose-built component, or an entry in the theme (`packages/brand/src/theme/heveta.ts`): its tokens, its `components` overrides, or a custom variant there (`astryx theme build` generates the variant's types beside it). If none of these can express it, report it instead of working around it.
- The theme is `packages/brand/src/theme/heveta.ts`, shared with the site (apps/site) and read by the desktop client for its own pages (apps/electron). It is compiled ahead of time with `astryx theme build` (`pnpm theme`; the outputs beside it are committed and `pnpm check` fails when they are stale) and loaded as a stylesheet from `app/app.css`, so `<Theme>` injects nothing at runtime; after editing it, run `pnpm theme`. It is Astryx Neutral re-toned (2026-10-02, after the user found the first, flat grey look heavy and dated): quiet and warm, as in Claude and ChatGPT. Ink is a soft black (`#1f1f1d`), never pure black, and greys lean warm. Two page steps: the frame (side nav, the desktop window's band, a page that stands alone) is an off-white a shade under the content, which is white. Things in the page (cards, a person's message) take the frame's shade, so they sit in the white without boxes drawn around them; cards use `variant="muted"`. Things over the page (the composer, menus, popovers, dialogs) are white and set apart by a hairline and a soft shadow that deepens with the layer (`--shadow-low/med/high`); the composer keeps its default `elevation`. Headings are semibold, never bold; conversation text is a step larger than the interface (15px to 14px). Banners are pale tints of their status. Lines that carry structure keep the border color: table rows, a quote's bar, rules, code block frames, field outlines, `Divider`s, a tab bar's baseline. Never make the border tokens transparent: that erased all of those. The focus ring and the inset state rings stay. Plus a few component rules the app needs, each commented with why. We are not designers: a coherent system's defaults look right, ad-hoc styling does not. No decorative panels, custom font sizes, or colors outside the theme. The logo (`BrandMark` in `packages/brand/src/index.tsx`, `public/favicon.svg`) is the only custom visual.
- "No customization" is per component: never restyle a component, but configure it freely through its exposed variants and props. Templates are references, not rules: when a template's default placement is unreasonable (e.g. SideNav's collapse chevron alone at the very bottom), follow mainstream agent apps instead.
- Consult the closest Astryx template and use the component built for the job (ChatLayout, ChatMessageList, ChatComposer, Markdown with `isStreaming`, ChatToolCalls, SideNav, Dialog, Selector, DropdownMenu, Tooltip). Do not restyle a generic component into something Astryx already provides.
- Follow mainstream AI agent conventions (ChatGPT, Claude): appearance lives in Settings, not persistent chrome; the composer is one box with an icon-only "+" menu on the left (adding content) and the model `Selector` in `sendActions` next to the circular send/stop button (how it is answered, as in Claude and Gemini); a new task centers the prompt and composer, which dock to the bottom once messages exist.
- Minimal is not bare: give options, setting rows, menu items, and statuses icons (`lucide-react`) when it helps people tell them apart.
- Interface text is functional: titles, labels, instructions, errors. No taglines or descriptions of what the agent can do. A thread is a "chat"/"conversation" in English and "对话" in Chinese ("New chat"/"新对话", "Search conversations"/"搜索对话"): people may just chat, not only hand over work, so keep the wording neutral as in ChatGPT/Claude. The same goes for prompts and placeholders.
- Every string the interface shows is a message: English (the default) and Simplified Chinese side by side in the feature's `messages.ts` (`defineMessages`), read with `useT()`. Never write text into a component. A module that produces text for the interface (a failure's reason, a form field's error, a setting's label) returns a `MessageKey` or `Message`, and the component translates it when it renders, so switching language updates what is on screen. Dates and numbers are formatted with the current locale (`useLanguage`), never a fixed one. Write English with typographic apostrophes (’) and the ellipsis character (…).

## Heveta integration

- The app uses Astryx's prebuilt integration: `app/app.css` imports `@astryxdesign/core/reset.css`, `@astryxdesign/core/astryx.css`, and the ahead-of-time compiled `@heveta/brand/theme.css`; Vite has only the React Router plugin (no StyleX compiler). `<Theme theme={hevetaTheme}>` (`color-mode.tsx`, and the nested previews in settings) supplies the theme scope and color mode. The compiled theme has `__built: true`, so Theme skips runtime CSS generation and injection. The stylesheet themes the prerendered loading shell from its first paint; the document-head script applies a saved light or dark mode before that paint. Keep the theme precompiled so its CSS loads and caches with the other static assets. Every `Theme` takes the compiled `hevetaTheme` from `@heveta/brand/theme`, never a published theme directly.
- Declare the CSS layer order (`reset`, `astryx-base`, `astryx-theme`) in the HTML head before any styles load (`root.tsx`), as well as in `app.css`, so development and production use the same order even when Vite injects `app.css` from script.
- Give `ChatLayout` a bounded flex-column parent. It owns message scrolling and the sticky composer; `Layout`'s content slot alone does not provide that flex parent.
- Use `alignment="end"` for menus triggered at the trailing edge of the viewport or mobile drawer.
- SPA mode (`ssr: false`) still splits the code by route: a page's module and its imports load when it is first opened, one import discovered after another, and React Router keeps the old page on screen until they are in. Opening settings waited on three round trips (~300 ms at 80 ms latency). A page reachable from a shell is fetched ahead with `PrefetchPageLinks` (all its modules at once, as `modulepreload`): the conversations prefetch `/settings`, settings prefetch the page "back" returns to, and sign-in the page it leads to (from "Sign in" to the page: ~1310 ms and 24 files fetched after the click, ~210 ms and 4 after, at 100 ms latency).
- Built files under `/assets/` carry a content hash, so `public/_headers` serves them `immutable` for a year (Workers Static Assets). With the default `max-age=0, must-revalidate`, every navigation that re-adds a route's stylesheet waited on a revalidation round trip before it rendered (the way back from settings took ~320 ms at 200 ms latency, 59 ms after).
- Heavy code that is rarely on screen stays out of the first load: a static import puts a module in its route's (or layout's) modules, which load before the page shows, even behind a closed panel or dialog (a closed `Dialog` keeps its children mounted). The computer's screen (noVNC, 194 KB) and terminal (xterm and its stylesheet, 342 KB) are `React.lazy` in `computer-page.tsx` behind a `Suspense` with a labelled `Spinner`; KaTeX (259 KB, 30 KB of CSS, fonts) loads with the first formula (`Formula` in `chat-bubble.tsx` shows the source meanwhile); the rename dialog (react-hook-form, zod: 122 KB) is mounted from the first rename on (`thread-shell.tsx`), not only while open, since `DialogHeader` focuses its title when it mounts and took the focus from a form that arrived in an already open dialog. Shared helpers live apart from heavy modules: the thread controller's `memoriesQuery` came from the memory settings page (`settings/queries.ts` now) and the profile's `authErrorMessage` from the zod schemas (`auth/errors.ts`), each bringing its whole module along. Cold load of `/` signed in (HTTP/2, 100 ms, 10 Mbps): 767 KB and the title at ~1750 ms before, 548 KB and ~1250 ms after (the modules the manifest lists for it: 743 KB gzipped, 483 KB after). The `/settings` prefetch still fetches the username dialog's form libraries (38 KB gzipped) on `/`, once the page's own modules are in. Check with the React Router manifest (`build/client/assets/manifest-*.js`, each route's `imports`) after a build, not with the source.

## Lessons learned (read before building or reviewing UI)

- Messages off screen are skipped in layout and paint (`content-visibility: auto` on `chat-message`, in the theme): a reply streaming at the end of a 100-message conversation redrew the whole transcript every frame (4x throttled, p95 83 ms, 105 frames over 50 ms; skipped, p95 17 ms, none). Skipping also contains a message's painting to its box, which cut the focus ring of the buttons at its edge; `overflow-clip-margin` gives it room, as a single length (Chrome ignores a `calc()` there, computing 0).
- The conversation controller is three contexts by how often each changes (`thread-controller.tsx`): the commands (the same functions for the provider's life, reading the latest state through a ref), the conversation's state (memoized on its fields), and the composer's draft (new at every key press, read by the composer alone). One context rebuilt at every key press and streamed word rendered the transcript's latest reply, its Markdown and formulas, and every consumer again: 235 components a key press, now 77, none of them a reply. Pass replies stable callbacks (`onRegenerate` plus `canRegenerate`), never a closure made in the render.

These came from real mistakes on this app. Check each one before calling a screen done.

### Choosing components and variants

- Astryx is new; don't use it from memory of other libraries. Every prop you leave unset has a default with its own behavior, so read the props doc and source for the defaults too, not only the props you set.
- Read what a component actually does before picking a variant: its props doc (`astryx component <Name>`) and, for spacing or layout questions, its source in `node_modules/@astryxdesign/core/src/<Component>/`. Defaults encode assumptions; a template's choice is not automatically right for us.
- Astryx chat components assume avatars and bubbles. We have neither, so:
  - Render assistant replies flush in `ChatMessage` (no `ChatMessageBubble variant="ghost"` — a ghost bubble keeps its padding and pushes text right of the action row).
  - Use `ChatLayout density="balanced"` (no own inset or width cap, scroll area stays full width) and cap `ChatMessageList` and the composer together to one centered 800px column (the theme's `chat-message-list` and `chat-composer` rules). `spacious` adds a second inset on top of `ChatMessageList`'s own.
- Props typed `IconType` (`SideNavItem`, dropdown/menu items, `Selector`'s `startIcon`) take the icon component itself (`icon={Search}`) so Astryx sizes it. Props typed `ReactNode` (`Button`/`IconButton` `icon`, a `DropdownMenu` `button.icon`, `SideNavCollapseButton` children, `ChatSendButton` `sendIcon`) take `<Icon icon={Search} size="sm" />`, never a raw `<Search />`: a raw lucide element renders at its 24px default and overflows. Button's icon slot is 16px (20px for `size="lg"`) while `Icon` defaults to `md` (20px), so `sm` is the fit, as Astryx's own buttons use.
- Something other than an icon in a Button's icon slot must fit the slot too: the collapsed rail's account `Avatar` is `xsm` (20px) in an `lg` button, with `tooltip={false}` because the button already names and tooltips it (the avatar's tooltip also adds a tab stop).
- `Button` centers its content in whatever width it gets (`justify-content: center`; the label does not grow), and no prop changes that; a content-width button cannot truncate a long label either. The expanded sidebar's account is still one full-width `DropdownMenu` button laid out as a start-aligned grid (avatar, name, chevron): the theme's custom Button variant `account` (a ghost button's colors plus the grid), used by `account-menu.tsx`. It is themed on purpose: the user chose this look on 2026-09-25 after an `Item` with a trailing menu button was tried and rejected. Do not "fix" it.
- `Button`'s `isLoading` makes its content transparent behind a spinner, so a label like "正在上传 42%" never shows. Progress is a `ProgressBar` beside a disabled button (the computer's file upload).
- `SideNavItem`'s `isSelected` means the current page (`aria-current="page"`). "Computer", "Terminal", "Files", and "Mail" are links to peer pages in the shared app shell, selected by the current route.
- `useAppShellMobile()` reads AppShell's context, so it only works below `AppShell`; in the component that renders AppShell it returns the defaults (never mobile). Page headers and `MobileNavToggle` consume that context instead of repeating the breakpoint in a media query.
- Astryx links go through our `LinkProvider` (`RouterLink` in `lib/app-provider.tsx`). It hands a path to React Router only when one of the app's routes matches it; any other same-origin path (a file at `/files/…`) is a plain anchor, a document request. Routing every "/" href made a file card open the SPA's 404.
- `Markdown` caps prose at `contentWidth` 680px by default; in our 800px column it is `"100%"`.
- Plain text as someone wrote it (an email's body) is `Text type="plain"`, a custom type in the theme (`whiteSpace: pre-wrap`, as a user's bubble keeps its line breaks); `Text` has no prop for it. `astryx theme build` generates declarations only for components' own `*VariantMap` interfaces, and custom Text types are the theme module's `CustomTextTypes`, so the type is declared by hand in `app/types/astryx-text.d.ts`, as Astryx documents (CLI 0.6.2). A new custom Text type goes in both places.
- The mailbox's folders (`/mail`, `/mail/sent`) are a `TabList` of `Tab`s with `href`, without `role` (navigation between views, a nav landmark with `aria-current`): the address is the folder, so `onChange` does nothing. The list and an email are one route module (`features/mail/mail-page.tsx`), fetched ahead from the side nav with `PrefetchPageLinks page="/mail"`.
- Icon color follows the control's rank. Astryx ghost buttons draw their icon in the primary text color, so auxiliary and row-level icon buttons pass `Icon color="secondary"`: the reply actions, the sidebar collapse toggle (SideNav's own item icons are secondary), a conversation row's `MoreMenu` (its `icon` prop, keeping the registry's `moreHorizontal` at `sm`), a table row's delete. Main controls keep the default: the composer's "+" and model picker, send, the phone top bar, back.
- A rare destructive action's trigger stays quiet (`variant="secondary"`, e.g. 记忆's "全部清除"); its `AlertDialog` action carries the destructive style (its default `actionVariant`).
- `Table` always runs its rows out to its container's padding edges (`--container-padding-*`). Bare in a page it overshot the column's text on both sides; inside a `Card` (as the memory list is, `variant="muted"` like `SettingsCard`) it meets the card's edges.
- Reply text drops OpenAI's own citation markers (U+E200 … U+E201) before rendering and copying: the models sometimes still write them around our search results.
- A failed reply says only "回复生成失败" with the retry button; the run's error text is English, for logs and the model.
- `ChatMessageMetadata` is one inline row (`timestamp · footer · status`). The reply's action buttons are its `footer`, alone; a stop or failure notice is part of the reply and goes in `ChatMessage`'s children (as Astryx's own error template does). Put in `timestamp`, it sat on the same line as the buttons.
- Every finished reply shows when it was made, right after its action buttons in the metadata `footer` ("复制 重新生成 2分钟前", left-aligned): `Timestamp` to the minute, as fixed text: `time` ("14:32") for today's replies, `date_time` ("2026年9月14日 14:32") before that. No relative time or `isLive`: a ticking "33秒钟前" on every reply re-renders for nothing. Not in the `timestamp` slot, which renders before the buttons and made them shift with the time's length; not at the far right, away from them. The action icons are `Icon color="secondary"`, one level below the reply text, as in ChatGPT and Claude (Astryx ghost buttons default to the primary text color). User messages and a reply still streaming show no time. Whether a reply shows its footer depends on that reply alone (its own run has ended), never on its place in the list: tying it to "the last message while a reply is pending" hid the previous reply's copy button and time for as long as the next message was being sent and answered. Only "Regenerate" belongs to the latest reply, and only while no reply is being made.
- Math renders through `Markdown`'s `components.math` with KaTeX (`math-expression.tsx`), in replies and thinking alike; a display formula wider than the column scrolls sideways in a `ScrollableArea axis="inline"`. Astryx parses only `$…$` and `$$…$$` (with currency guards: "$20 and $30" stays text); `\(…\)` and `\[…\]`, which the models tend to write, lose their backslash to Markdown escaping and show as plain text. The server asks for dollars in the trailing developer message of each request (`agentConfig.replyFormat`); in the system instructions the models ignored it at low effort. Don't rewrite `\[…\]` in the client: the component cannot be taught it, and a text rewrite must dodge code and split deltas.
- `ChatToolCalls` takes every call of a run in one `calls` array (it groups them itself), each with a `target`. `CodeBlock`s in `resultDetail` get `width="100%"`, `isWrapped` and a `maxHeight`; its default `fit-content` width and unbounded height stretch the transcript. `ChatToolCalls` itself gets `maxWidth: 100%` (the theme's `chat-tool-calls` rule): `ChatMessage` lays assistant blocks out at content width (`alignItems: flex-start`), and a row's one-line target counts its whole length toward that width, so a long shell command ran the row past the column and its ellipsis never applied.
- `ChatSendButton`'s accessible name is fixed ("发送"/"停止"), and its stop state cannot be disabled. The stopping state is a disabled send state with the `stop` icon, named via `aria-labelledby` by the "正在停止…" status text.
- Search is a `CommandPalette` with an async `SearchSource` (debounce inside `search`, abort in `cancel`, recent conversations from `bootstrap`); it keeps the previous results while a query loads. Astryx's zh-CN catalog lacks its footer hints, so the footer is ours.
- `ChatLayout` is the conversation's scroll container and leaves the native scrollbar unstyled (a 15px bar with a grey track that takes layout width, shifting the centered column when a conversation starts to scroll). It gets the presentation Astryx's own `ScrollableArea` uses (`scrollbar-color` neutral thumb on a transparent track) from the theme's `app-shell` rule, and no `scrollbar-gutter` is reserved. Where scrollbars always show, `stable` leaves an empty strip on the right of every short conversation (right gaps 15px wider than left) and `stable both-edges` one on both sides (reads as an extra outer padding); keeping the layout symmetric matters more than the one-time ~7px shift when a conversation first becomes scrollable. Don't override `scrollbarWidth`: ChatLayout uses it to hide the bar during animated scrolling.
- Don't patch or fork Astryx source to fix its bugs. Work within its props; when no prop covers it, leave it and report it upstream. Known: ordered-list numbers in `Markdown` wrap from 10 on ("12" over "."), because `ListItem` gives the number a fixed 16px width, and `Markdown`'s `components` cannot replace lists (as of 0.6.3). And `ChatToolCalls` cuts the tool's name by a few pixels ("运行命…") when the target is long: the name shrinks with `flexShrink: 1` against the target's `10`, and flex shrinking is weighted by each item's content width, so a very long target still takes up to a tenth of the overflow from the name. Cutting the target to some length does not fix it at every width; leave it.
- Popovers from the bottom-docked composer open upward: `placement="above"` on the "+" `DropdownMenu` and the model `Selector`. Selector's default (no `placement`) overlays the selected option on the trigger and extends the rest below it, off the page; the prop is documented only in the source JSDoc, so read the source when the CLI docs lack a behavior.
- Attachments are any file (up to 10 in a message, 100 MB each; the client mirrors the server's limits in `features/files/kinds.ts` to say so before uploading). They upload through `POST /upload` with XMLHttpRequest (fetch reports no upload progress), not an RPC. In `ChatComposerDrawer` (without `count`: its collapse toggle is not worth it for ten files) images are `Thumbnail`s in one row and other files `Token`s with a kind icon and the upload percentage in another, as in Astryx's composer-attachments block. In messages, too, images and other files are separate rows: in one row the file cards stretched to the image's height. The "+" menu has one item per kind, as in ChatGPT and Claude: "添加图片", "添加 PDF", "添加文件"; images and PDFs are what the model reads itself, so with a model that cannot, those two are disabled with the reason.
- `Thumbnail` is a compact square preview: right for composer attachments, too small for the transcript. Images in messages use `AspectRatio` at the image's natural ratio, capped at 320px on the longer side (the ratio comes from the file record's `width`/`height`, which the server reads from the image's start when storing it, EXIF rotation applied, so the box has its shape before the image loads; a file without them is measured on load), inside a borderless `ClickableCard` (`variant="transparent"`, `padding={0}`) that opens the `useLightbox` view: the whole image is one control, and the card clips it to rounded corners.
- Theme `components` targets sit on specific elements; read which. Every floating surface (DropdownMenu, Selector, ComplexSelector, Popover) is the `popover` target; `dropdown-menu` is the list inside it, so a token re-pointed there never reached the surface's background.
- `SideNav` always renders its footer icon row, empty or not, and its gap: an account passed as `footer` sat 16px from the bottom. The account goes in `footerIcons`, which the rail keeps when collapsed.
- A conversation row's `MoreMenu` shows only where it is useful, as in ChatGPT and Claude: on the selected row, on hover or keyboard focus within the row, while its menu is open, and always on devices without hover (`(hover: none)`). The same items open from a right click (or long press) through `ContextMenu` around the row (`ThreadRow` in `thread-shell.tsx`).
- Don't put interactive controls inside a link: `SideNavHeading` with `headingHref` wraps `headerEndContent` in the anchor.

### Placement follows mainstream agent apps, not component defaults

- Sidebar: collapse toggle in the header next to the product name (`collapsible={{ hasButton: false }}` + `SideNavCollapseButton` in `headerEndContent`), account alone at the bottom, collapsed rail shows icons plus an expand item, collapsed state persisted per viewer, account menu icon-only (`useSideNavCollapse`) in the rail.
- Navigating away from "Computer" releases the screen or terminal connection, while server-owned runs continue. Only the explicit computer management actions in Settings restart or clear the computer.
- Mobile drawer: pass our own `<MobileNav side="start">` as AppShell's `mobileNav.content`. `MobileNav` defaults to `side="auto"`, which picks the edge from the focused trigger; tapping a button on a phone focuses nothing, so it fell back to the end edge and the nav slid in from the right. SideNav's drawer mode cannot set `side`. The drawer's content region is a plain scroller, so put nav items, the list (flex-grow), and the account in one full-height `VStack` to keep the account at the bottom.
- Conversation page on desktop has no bar above `ChatLayout` (Astryx's AI Chat template, ChatGPT): the composer floats inside the scroll area, so a bar outside it made the scrollbar start below the bar yet run past the composer to the bottom. `Layout` cannot float a header over scrolling content without custom sticky styling, so the title lives in the side nav's selected row, the tab, and a `VisuallyHidden` h1. Phones keep the bar for the drawer toggle and "新对话" (their scrollbars are overlays).
- Landing: one line, a time-of-day greeting with the user's name in `display-3` (29px; `display-2` read as too large), then the composer, as in Claude and Gemini. Nothing else: a mark and a second line ("What can I help with?") over it were removed on 2026-10-02 as weight the page did not need, and category/suggestion chips before that as clutter.
- New conversation: desktop centers greeting and composer together; phones keep the composer docked at the bottom. The landing composer uses the same 800px column and the dock's inline padding, so its width does not change when the first message docks it.
- "新对话" is an action and never shows as selected; ⌘K / Ctrl+K opens "搜索对话", as in ChatGPT.
- On touch devices (`(pointer: coarse)`) Enter in the composer inserts a line break and only the send button sends; desktop keeps Enter to send, Shift+Enter for a new line.
- A conversation that does not exist (`NotFound`) shows an `EmptyState` with a "新对话" action and no composer, not a retry banner.
- Settings is its own layout that replaces the whole app, as in Linear or GitHub: `/settings/:section` sits beside the conversation layout (not inside it), and its side nav holds "返回" (back to the page settings was opened from) and the sections, never the conversation list. Phones get no side nav there: `/settings` lists the sections and each section has a back button. A new section is one entry in `settings-sections.tsx`. Section content is one 720px column centered like the conversation page, via `Layout contentWidth` (the scroll area stays full width); left-aligned content left the right half of wide screens empty. Rows use `SettingsCard`/`SettingsRow`; lists of records (memories) use `Table`, whose cells wrap (a `ListItem` label is single-line and cuts long text).
- Sign-in is one page (`/signin`): email, then the code sent to it; the first sign-in creates the account. The code goes back with the challenge `SendSignInCode` returned (a resend brings a new one): wrong guesses count against that code alone, so someone who knows the email cannot use up or replace its owner's code. A signed-out visit to a page goes to `/signin?next=<that page>` and back there after sign-in (`require-session.ts`, same-origin paths only); a signed-in visit to `/signin` goes on. Signing out, here or in another tab, leaves the signed-in pages at once (`SignedInLayout` watches the remembered account). No passwords, sign-up, or reset pages. The session is an HttpOnly cookie the app never sees (apps/server/README.md): the store keeps only which account this browser is signed in to, so pages open at once, and the server's answer (`confirmSession`, on opening and whenever a request is refused as unauthenticated or the event channel cannot open) corrects it. Signing out waits for the server, which alone can clear the cookie; until it has, the browser is still signed in. The client's auth interceptor and the server's list the same public AuthService methods; every other request, `UpdateCurrentUser` and uploads and downloads included, names the account the page acts for (`X-Heveta-User`, `?user=` on WebSockets), and the server refuses one whose session is of another account.
- The thread controller lives in the signed-in parent layout, above both the conversation and settings layouts, so an unsent draft and running replies survive a visit to settings.
- Appearance lives in Settings, nothing theme-related in persistent chrome. It is three `SelectableCard`s with a miniature of the app in each mode (after Astryx's settings-dialog template: a nested `Theme` per preview keeps the light card light in a dark app; "follow system" is half of each), placed in the row's `detail`. A `Selector` suits many choices; a few visual ones read better as pictures.

A bare `Center` painted nothing, so the browser's own canvas showed (white, or its near-black in dark mode), and the desktop client's band did not match it.

### Loading and hydration

- The app is an SPA whose prebuilt HTML shell is rendered in "system" color mode. Hydration does not patch mismatched attributes, so client state that changes markup (the saved color mode) must start from the shell's value and switch in a layout effect, which lands before the first paint. A head script sets `data-theme` on `<html>` from storage so the page is right before any JS runs.

### Verifying

- Change only what was asked or what a measured problem requires; don't add speculative "improvements". Before reporting a change, measure every state it can affect, not only the one that motivated it: left and right gaps, short and long content, always-visible scrollbars (desktop Chrome at 700px and 1280px shows them) and overlay ones (phone), light and dark. A scrollbar-gutter tweak verified only for the case it targeted broke left/right symmetry twice.
- When something looks misaligned or too padded, inspect the DOM (bounding rects and computed padding up the ancestor chain) and read the component source to find the exact cause. Do not guess or brute-force variant combinations.
- The state logic (run revisions, list updates from events) has unit tests in `test/`: `pnpm test` (vitest, with its own `vitest.config.ts`, not the app's Vite config). Change that logic with a test.
- A dev server may already be running (5173/8787); a second `pnpm dev` moves to 5174/8788. Check which one you test against, and stop only your own process tree.
- When the ego browser's `Page.captureScreenshot` times out (its window is not drawing), screenshot with a separate headless Chrome (`--headless=new --remote-debugging-port`) driven over CDP, with the signed-in `localStorage` copied over from the ego page.
- Test phone layouts with touch emulation (`Emulation.setTouchEmulationEnabled` plus `Input.dispatchTouchEvent`), not mouse clicks: a click focuses the button, a tap does not, and components that read focus behave differently.
- Before reporting UI work, screenshot every affected page and state on desktop and phone, light and dark: empty, loaded, error, menus and dialogs open, collapsed sidebar, drawer. Compare each against how ChatGPT or Claude would lay it out.
- Transitions flash when a state change goes through an intermediate frame, too short to see in a screenshot. Record the DOM on every mutation (a `MutationObserver` logging the path, composer text and focus, whether the composer or message list element was replaced, and any loading indicator) across the whole action; `requestAnimationFrame` sampling stalls in a background tab.
- Copy stays functional and user-facing: no taglines, no jargon ("凭据" → "密码"), no redundant hints the control already enforces (e.g. "最多 200 个字符" under a field with `maxLength`).

## State boundaries

- Keep UI changes separate from the RPC protocol and run/session state. Preserve thread-scoped drafts, upload cancellation, and server-owned tools.
- `ThreadSubmissions` owns start/cancel commands and draft acknowledgement; navigation, logout, and unmount never cancel server execution. A send whose outcome is unknown goes out again with the same request ID (backing off to 30 s, at once on reconnect): the server takes a request once and answers a repeat with its run, so there is no "confirming" or "uncertain" state to show. Only a refusal puts the message back in the composer. Stopping while it is being sent stops its reply once the server has it; a sent message stays sent.
- The conversation's message list is the only source of what it shows, the reply being made included: an assistant message carries its run as of that copy (`runStatus`, `runAttempt`, `runCancelRequested`, `runRevision`), run events update it in the list (`showRun`, `applyRunChangeToList` in `queries.ts`), and the composer follows the list's latest reply (`latestReply` in `thread-controller.tsx`). A separate run cache and an observer that chose which run a conversation showed made two sources of the same reply, kept apart by comparing message IDs.
- The controller belongs to one session: `SignedInLayout` keys it by user and session version, so another account signing in mounts a new one instead of resetting its parts.
- RPCs are request/response only; every change arrives on the user's event channel (`features/events/event-channel.ts`, a WebSocket at `/events`, docs/sync.md), opened once by `ThreadController` after sign-in. Don't add a streaming RPC or poll for changes: publish an event on the server instead. Apply each run's events in arrival order (`run-sync.ts`); a missing revision, or a reply the list lacks, recovers a complete snapshot with GetRun before applying more. A conversation nobody has loaded takes nothing. Events are not replayed: each (re)connect reads again the user's queries on screen.
- Apply every `RunChange` atomically at its revision.
- Sending is optimistic, as in mainstream chat apps: the message leaves the composer at once (the submission holds its text and images) and shows in the transcript until the server's copy replaces it in the same render (`events.accepted` before `drafts.accept`); a failed send hands the text and images back to the composer, and says so in a toast when it failed in a conversation not on screen. The server's copy is a new element with the server's image address, never loaded on this device, and the image went blank until it loaded (39 frames at 400 ms latency): the images this device sent keep their local copies past acceptance (`features/files/local-images.ts`), and `MessageImage` shows the local one (an address the page has loaded shows at once in a new element) until the server's has loaded, then switches the same `<img>`, which keeps its image until the new one is ready. The composer stays editable; only adding images waits. Whatever brings the new run's snapshot first confirms the send (`ThreadSubmissions.acknowledge`): the event channel usually beats StartTurn's response, and waiting for the response showed the message twice meanwhile; it also confirms a send whose response was lost.
- A new conversation is created by its first StartTurn (empty `threadId`), so a lost response or a stop never leaves an empty conversation. It must not pass through an empty frame: on acceptance the draft moves to the new thread and stays visible at the old key until the page has navigated (`ThreadDrafts.move`/`followed`); the page renders the controller's `threadId` (the draft's), which runs ahead of the URL; the conversation record and sidebar entry are seeded before navigating; and `ChatLayout` is keyed by the draft (`viewKey`), not the URL. The landing-to-conversation layout switch remounts the composer (ChatLayout can only dock it, so the centered landing is a different tree), and the new one is not refocused: ChatComposer draws its keyboard focus ring when its editor gains focus while Astryx's last interaction was the keyboard, so a refocus after the Enter that sent lit the ring, which read as a flash. The cost is a click before typing the second message; keeping focus without the ring would need the composer not to remount.
- A send the server refused (InvalidArgument, FailedPrecondition, NotFound, …) was not committed: show its reason, never "retry", and resend with a new request ID. Only an unknown outcome (network, timeout, 5xx) is recovered by looking the request ID up.
- Tabs share one login: they share the cookie, and another tab's sign-in or sign-out reaches this one through the stored account's `storage` event (`adoptUser`).
- Only a run known to be active is watched; a finished run is read once, and its messages are reloaded only when this page saw it finish.
- Run events update a conversation's message list only once it is loaded (`showRun`). Creating the list from an event held only that run's messages and, being fresh, kept the history from ever loading. Events that arrive while a query is being read (a message list, the side nav, a conversation's record) apply again on top of the response, which may be older than they are (`applyChange` in `queries.ts`): a conversation deleted during a reread came back. The side nav likewise inserts a conversation only into the loaded page it belongs to (`insertIntoPages`): each page starts below the previous page's lowest ID, so one below every loaded page arrives with "加载更多", and inserting it earlier listed it twice.
- A side nav row shows a spinner while a reply is being written in its conversation (`Thread.running`, as its `endContent`, beside the row's menu), so a long reply is seen going on from any other page, on every device, as in ChatGPT and Claude. Not on the row of the conversation open now: its reply shows itself being written, and a second, moving signal at the edge of view only distracts. It is merged by the conversation's activity time, the time its latest run began (`latestActivity` in `queries.ts`, docs/sync.md): records, `ThreadActivity`, and every run event of any conversation, loaded or not, feed it (`showThreadRun`). A change that leaves a query's data as it was writes nothing (`applyChange`): run events come at every commit, and each redrew the side nav.
- A reply shows how its run ended ("已停止", "回复生成失败") from the observed run for the latest reply and from `Message.runStatus` for earlier ones; the run state keeps the output's `runStatus` equal to its run's.
- "连接中断，正在重新连接…" shows once the event channel is down: dropped, or its first attempt failed (a reply otherwise spun with no word while nothing could arrive). While the first attempt is under way nothing is lost, and the reply loader stays. Each (re)connect cancels reads under way before invalidating (a query without data joins a read under way instead of repeating it) and sends the unconfirmed messages again at once. Coming back to the page pings an open channel at once.
- A render error replaces only its page (`ErrorBoundary` in `thread-page.tsx` and `settings-page.tsx`), never the signed-in layout: there it unmounted the thread controller, which dropped every unsent draft and deleted their uploads. Opening another page leaves it.
- RPCs fail after 30 s (`defaultTimeoutMs`), so a stalled call cannot hold its dialog or the event channel's reconnection; `computerClient` has no default, since waking the computer can take minutes and the deadline reaches the server.
- A file from the computer downloads through `fetch` and a blob URL, not by navigating to `/computer-file`: a failed download replaced the app with the server's JSON error and lost unsent drafts.
- A queued run shows the same reply loader as a starting one; a "waiting to start" label flashes for a moment on every send.
- A pending stream is not a reasoning signal. Show one reply loader before text arrives or while awaiting text after a tool result; tool rows and the thinking block ("思考中…") own their activity indicators. `Spinner`'s `label` is visible text; use `aria-label` for an indicator without a caption.
- Thinking is the model's summary, a `reasoning` part, shown folded above the answer as in ChatGPT and Claude. Consecutive reasoning parts are one block. The provider omits summaries at random (with `"auto"` and `"detailed"` alike), so a reply may have none: no summary, no block; the reply loader covers the wait. Summaries come in English.
- Thinking and tool calls are one activity, as in Claude: each stretch of reasoning and tool calls in a reply is one block (`Activity` in `chat-bubble.tsx`) that looks the same whether it is being written or opened later. Its title row copies ChatToolCalls' own (a `Button` of the theme's `disclosure` variant: an icon, the text, and the chevron right after it, the icons at the text's 12px (`xsm`) and the leading one in the button's children with the text, since Button's `icon` slot is a 16px box that inset it, in ChatToolCalls' small text and no taller than its line, with no inline padding so the icon lines up with the reply's text (a Button's own inset indented it), and no hover or press tint or press shrink (the variant sets the overlay colors transparent), as ChatToolCalls' title has none; lucide chevrons, as the icon registry has no up chevron): while it is written, one line: a spinner and the call under way with what it acts on ("Run command sleep 6 && echo done"), or "Thinking"/"思考中" while the model thinks or reads a result; once the model answers, the icon of what it names and "N steps"/"N 个步骤". It stays closed unless opened (it once opened itself while written, which showed the running call twice, in the title and in its row, each with a spinner), and no other loader shows under it: one progress indicator at a time. Opened while written it is the `activity-live` card (a few lines high, following the newest step); opened after, the `activity` card in full, no nested scroller. It is the reply's width, so a long command or URL is cut to fit instead of widening the page on a phone. Call names are for people, so the theme sets them in the body face inside ChatToolCalls (which uses the code face, as for function names); code blocks there keep the code face. Files the agent sends, commentary, and the answer stay outside it, in order. The summary's per-step bold titles are not structured data, so the title does not show them (no regex over Markdown).
