状态（2026-09-24）：

- **也已实现：** 第 5 节的工具执行分离与沙箱（每个用户一台电脑，见 [sandbox.md](sandbox.md)），包括电脑屏幕上那个浏览器的操作工具（Playwright MCP）。
- **增量存储已实现并部署（2026-09-30）：** [Run 存储契约](run-storage.md) 取代原 `run_items` 提案；DO SQLite 保存活动增量与原生工作窗口，定稿分块归档 PostgreSQL。模型结果未知仍不重放；服务商明确拒绝的请求不在此列，见第 2 节。
- **2026-09-29 修订：** 服务商暂时拒绝的模型请求改为退避重试（第 2 节）；文件（图片、PDF）按预算清理最旧的而不是省略最新的、被清理结果的提示区分有无副作用、上一轮过长时可以整段滑出、默认 token 比例改为实测值（第 3 节）；请求的组成与提示词缓存（第 3 节“请求的组成”）；记忆作为引用的数据注入（第 4 节）。

以下为原方案。依据是对现有代码的梳理和对主流 agent 的调研（Claude Code / Claude Agent SDK、OpenAI Codex / Agents SDK、Manus、ChatGPT 与 Claude 的记忆、Cloudflare Agents）。标注「待决定」的条目需要拍板后才实现。现有执行模型见 [agent-runtime.md](agent-runtime.md) 与 [agent-model.md](agent-model.md)。

## 1. 现状

- `runtime/loop.ts` 每个 Run 只调用一次模型。模型返回工具调用时报 `unavailable capability` 并失败。
- 预算：最多 8 个模型步骤、12,000 输出 tokens、单步 4,096、120 秒（`config.ts` 的 `agentConfig.limits`）。停止原因里有 `STEP_LIMIT`、`TOKEN_LIMIT`、`TIME_LIMIT`，Run 状态里有 `LIMIT_REACHED`。
- 上下文：（已由第 3 节的滑动窗口取代）当时取最近 200 条消息，按 JSON 字符数（60k）从最老的一轮整轮丢弃。
- Checkpoint：每次保存都重写整份 transcript。步数一多，写入量按平方增长。
- `deadlineAt` 同时承担两件事：执行时长预算，以及瞬时错误退避重试的上限。
- 已有基础：模型请求前先落库、DO alarm 恢复、Step 持久化、事件与 revision 同步。协议里已有 `ToolCall` / `ToolResult` 消息片段，前端 `ChatToolCalls` 已经能渲染。

## 2. Agent 循环

**原则（已定）：** 循环不设预算。模型不再调用工具时自然结束；只有用户停止能提前结束。这与 Claude Code / Claude Agent SDK 一致（`max_turns`、`max_budget_usd` 默认不限），Codex 也没有步数上限。

循环：

```text
loop:
  组装上下文（第 3 节）
  调用模型（流式）→ 追加模型输出
  没有工具调用 → 结束（MODEL_COMPLETE）
  执行工具调用 → 追加工具结果（成功或错误都作为结果交给模型）
```

设计要点：

- **去掉预算：** 删除 `modelSteps`、`outputTokens`、`outputTokensPerStep`、`durationMs`，以及 `STEP_LIMIT`、`TOKEN_LIMIT`、`TIME_LIMIT` 和 `LIMIT_REACHED`。请求不再传 `max_output_tokens`。停止原因只剩 `MODEL_COMPLETE`、`CANCELLED`、`ERROR`。
- **上下文窗口不是预算：** 它是模型的物理限制，由第 3 节的滑动窗口处理，不作为停止条件。只有单条内容本身就放不下时才失败，并说明原因。
- **重试上限另立：** 瞬时错误（数据库、R2、网络）继续按退避重试。上限改为「连续失败且没有进展的次数」，比如连续 5 次后判为 FAILED，不再依赖总时长。排队投递的截止时间是基础设施问题，保留。
- **工具错误回给模型：** 用 `is_error` 标记，由模型换一种做法，不终止 Run。这是 Anthropic、OpenAI、Manus 的共同做法。
- **并行：** 只读工具可以并发执行，有副作用的工具按顺序执行。每个工具在注册表里声明自己是只读还是有副作用。
- **持久化改为追加（方案已修订）：** 原先拟新增 `run_items` 表。现采用 [Run 增量存储设计](run-storage.md)：DO SQLite 分块追加公开输出与私有原生项，Checkpoint 保留阶段和游标；PostgreSQL 保存受理与控制记录，结束后分页归档公开内容。完整读取、取消、文件引用和部署交接一起修改，避免只迁上下文而公开消息仍全量重写。
- **服务商明确拒绝（已实现，2026-09-29）：** 模型请求在生成任何内容之前就被服务商拒绝，而且是稍后可能接受的那种（限流 429、超时 408、冲突 409、服务商自身 5xx，或响应带 `x-should-retry: true`，与 OpenAI SDK 自己重试的范围相同；请求根本没有得到回答时也算），这次请求确定什么都没发生。以前它和“结果未知”一样让 Run 直接失败，用户重试时只能从之前的轮次重建，这一轮已做的工作全部丢失。现在 loop 把这个 MODEL Step 记为失败、检查点退回 `ready`，由 actor 按已有的瞬时故障机制退避后从这个检查点继续（连续失败上限不变，5 次后结束 Run）。稍后也不会被接受的拒绝（400 请求不合法等）仍然直接失败。请求改为不经 OpenAI SDK 的客户端发送（见第 5 节的“内存”），所以 SDK 自带的两次快速重试不再有，由这里的退避代替。
- **模型响应后的提交（已实现，2026-09-29）：** 模型完整回复之后的那次提交（`tools` 检查点或 Run 的终态）如果因为数据库短暂故障失败，这个回复就再也拿不回来（结果未知的模型请求不重放）。所以记录了操作结果的提交（模型回复、工具结果、Run 终态）改为约一分钟内指数退避重试 8 次（0.5、1、…、32 秒），能挺过短暂的数据库中断或切换；其余边界（发出请求前的 `model`、`ready`）失败了下一次执行可以从上一个边界重来，仍然只试 3 次。
- **中断恢复（待决定 A）：**
  - 模型步骤：现在的规则是结果未知的模型请求一律不重放；未请求停止时 Run 结束为 FAILED，在途 MODEL Step 记为 INTERRUPTED（Run 没有 INTERRUPTED 状态）。长任务里 DO 被驱逐很常见，这会让几百步的任务因为一次驱逐前功尽弃。**建议改为重放**：模型请求没有外部副作用，重放只多花一次钱。
  - 工具步骤：只读或幂等的工具可以重放；有副作用的工具，结果未知时不重放，而是给模型一个「结果未知」的工具结果，由模型决定下一步。
- **以后再做：**
  - 运行中插话：用户在运行中发的消息先排队，等当前这批工具调用执行完再注入，与 Claude Code、Cursor 相同。
  - 外部副作用审批：发邮件、付款、发布这类动作先停在「待确认」，用户确认后继续。
  - 子 agent：放在独立的 DO 里，有自己的上下文，只返回 1–2K tokens 的摘要。

## 3. 上下文管理：滑动窗口（已定，2026-09-24）

不写摘要，也不做压缩。上下文超过阈值时，先清理旧的工具结果，再从最早的部分开始整段滑出；滑出的内容仍在数据库里，模型用搜索工具找回。

**组装顺序：固定的在前，会变的在后。** 提示词缓存按前缀匹配，任何位置一变，其后全部失效。

```text
[系统指令 + 工具定义（固定）]
[记忆列表（一次执行内固定，作为引用的数据，user 角色）]
[滑出提示（两次滑动之间固定）]
[窗口内的历史（只往后追加）]
[本次 Run 的 items（只往后追加）]
[邮箱地址 + 当前日期 + 回复格式要求（developer 角色，每次请求放在最后，不存进历史）]
```

请求的组成和缓存的实测与取舍见本节末尾“请求的组成与提示词缓存”。

**工作窗口。** 模型清单为每个模型配置 `contextWindow`，取的是“工作窗口”，不是模型上限。Codex 的模型配置给 GPT-5.6 Luna、Terra 和 GPT-6 Astra 用的都是 27.2 万 token，而模型本身支持 105 万。上下文越长，每一步重发的费用越高，准确率也会下降。

**触发与目标。** 用量达到工作窗口的 80% 时，一次性处理，降到 20%。只在触发的那一步让缓存失效一次，两次滑动之间尽量隔得久：

- 每一步都滑一点：每一步都不命中缓存。
- 降到 50%：比降到 20% 多滑一倍的次数，每次还要按原价重算更多内容。

同类做法对照：

- MemGPT：100% 时挪出半个窗口的消息。
- Codex：90% 时压缩到只剩摘要和用户原话。
- OpenAI 接口的 `truncation: "auto"`：每次只丢刚好够的量，最伤缓存。

**触发时的两步（同一时刻完成）：**

1. **清理旧工具结果**：除最近 3 次外，其余工具结果的正文换成一条说明，调用本身（工具名、参数）保留，所以可以恢复（Manus 的“可恢复压缩”、Anthropic context editing 的做法）。说明按工具是否只读（`ToolSpec.readOnly`）区分：只读的写“需要时用相同参数重新调用”；有副作用的（发邮件、执行命令、写文件）写“这次调用已经执行并生效，不要为了看输出而重复”，否则模型照着提示重做一遍，就是把邮件再发一次。
2. **滑动**：仍超过 20% 时，从最早的开始整段移出，工具调用与结果成对移出。
   - 永远保留：当前这一轮的用户消息，以及这一轮自己最近 3 次工具结果。
   - 更早的一轮总是整段移出，哪怕最近 3 次工具结果在它里面。以前保护的是整个窗口里最近的 3 次结果：新一轮刚开始、自己还没有结果时，这 3 次都在上一轮里，而上一轮是一个整体，于是它移不出去；上一轮自己的记录超过工作窗口时（几百步的长任务），窗口就再也滑不动。
   - 最前面放一条滑出提示：更早的 N 轮已不在上下文中；附上被移出部分里的用户原话（从新到旧，上限约 8,000 字符，用户的要求和约束多在这里）；需要细节时用 `conversation_search` / `conversation_read` 查当前对话。

**状态与缓存。**

- 跨轮次：切点记在 Thread 上：窗口从哪条消息开始、哪条消息之前的工具结果已清理、哪个文件及其之前的文件已清理。每轮开始时按切点从数据库重建上下文，同样的消息重建结果相同，前缀稳定。只有重建后仍超过 80% 时才重新计算切点。
- 一轮之内：长任务中途触发时，只在内存里处理，并写入运行检查点，不改 Thread 上的切点；下一轮开始时按上面的规则处理。

**文件（图片、PDF）。** 模型自己读的文件不算在字符里，有自己的预算：一次请求合计 20 MiB（`agentConfig.limits.modelFileBytes`，按文件记录的大小）。规则与工具结果相同：达到预算的 80% 时，从最旧的开始把文件换成一条说明（“为给更新的文件腾地方，已从上下文中清除”），降到 20%；文件旁边的文字（附件说明、工具结果的文字）保留。不清理的：当前这一轮用户消息里的附件（必须读到，发送时已检查不超预算），以及末尾模型还没看过的工具结果里的图片。清理写进这次 Run 的记录本身，之后的请求前缀不变，直到下一次清理。

以前是按从旧到新的顺序花预算，超出的省略：一个 Run 里连续截图，省略的恰恰是模型刚截的那张；新一轮开始时超出预算的旧轮次整段滑出，上一轮的问答连文字一起丢掉。现在清理的是最旧的图片，问答本身不动。

**计算 token。**

- 不逐条统计，也不存每条消息的 token 数：各家分词不同，同一段话在不同模型里的 token 数不一样。
- 用量按“字符数 × 这段对话自己的比例”估算。比例取自上一次模型响应的精确输入 token 数 ÷ 那次请求的字符数，按对话记录。中英文比例因此自动不同，不写死。
- 字符数直接从已加载到内存的消息计算，只在判断是否触发时计算。
- 请求里有图片或 PDF 时不校准：它们的 token 不在字符里，会把比例抬高。所以对话从第一轮就带着图片时，比例一直是默认值。默认值原来是每字符 1 token，窗口在大约五分之一的大小时就滑动；现在按实测改为 0.25：本地 31 个对话最后一次实测的比例，GPT-5.6 Luna 的 10%–90% 分位是 0.15–0.22（中位数 0.17，最高 0.38），DeepSeek Flash 是 0.24（2026-09-29）。略高于多数，宁可早滑。没有按文件估算 token 再扣除：各模型的图片计价方式不同（按尺寸切块、按页），PDF 的页数也不知道。

**界面。** 数据库里的消息一条不删，用户看到的永远是完整对话。是否在切点显示分隔线待定。

**不做：**

- 摘要。
- 模型自记笔记（Codex 的实验功能 history/notes 在清空整个窗口后需要它；我们是滑动，最近的内容一直在）。
- 单独的 history 工具：当前对话和历史对话是同一份消息，用同一组工具。
- OpenAI 原生 compaction：结果加密，只有 OpenAI 模型能读。

**已知风险。** 模型可能想不到去搜被滑出的内容。用户原话保留在滑出提示里，要求和约束一般不会丢；实际出现问题再考虑加笔记。

- 加密推理内容（reasoning）只在同一个模型内延续，不跨模型传递（现状已如此）。

**请求的组成与提示词缓存（2026-09-29）。** 线上 AI Gateway 的记录：GPT-5.6 Luna 每轮第 2 步起输入的 87% 命中缓存，每轮第 1 步只有 33%。原因和处理：

- **没有 `prompt_cache_key`。** 不带它时服务商按请求开头的一段 token 分配缓存所在的机器，而所有对话的开头都是同一份系统指令和工具定义，全部挤进同一处缓存。现在每个请求带 `prompt_cache_key` = 对话 id，同一对话的请求去往它前缀所在的地方。实测（本地 Worker 经 AI binding）：GPT-5.6 Luna 的响应原样带回这个值，同一个 key 的第二次请求 2,423 个输入 token 中 2,420 个命中缓存；DeepSeek 的 Responses API 接受它（不报错，响应里为 null）。
- **记忆、邮箱、日期放在记录之后，每步都不缓存。** 记忆最多 100 条、每条 500 字，每一步都按原价重算。现在记忆放在记录之前（系统指令之后），一次执行内不变，每一步都在缓存的前缀里；记忆被修改的那一轮之后，下一轮的第 1 步从这里开始不命中一次。没有放在“历史之后、本次 Run 的 items 之前”：下一轮按产品数据重建这一轮的 items（没有推理项，见下），它的前缀在这一轮 items 开始的地方就断了，放在那里的内容下一轮仍要按原价重发。邮箱地址和日期仍放在最后，和回复格式要求在一起：日期每天变，放在前面每天会让整个对话的前缀失效一次，这两项又都很短。回复格式要求必须在最后（放在系统指令里模型在低推理强度下不遵守，见 `agentConfig.replyFormat`）。
- **工具参数被重新序列化。** 下一轮从产品消息重建上一轮的工具调用，参数原来存成 jsonb 对象再 `JSON.stringify`：jsonb 会重排键的顺序（按键长），和模型原来写的文字不同。现在消息里存模型原样写的参数文字（`ToolCall.arguments`），发回模型的就是它自己写的那段；界面看到的是解析后的对象（`part-codec.ts`）。迁移 `conversation_text` 把已有的参数转成文字。
- **做不到的部分。** 请求带 `reasoning.context: "current_turn"`，推理项只在当前这一轮渲染给模型；上一轮最后一次请求里渲染了推理，这一轮重建时没有，两边的 token 序列在上一轮第一个推理项处就不同了。所以每轮第 1 步最多命中到上一轮的用户消息为止，上一轮 items（工具结果往往很长）要按原价重发一次，之后各步再命中。要改这一点只能按原样重放服务商的输出项（带推理、改为 `all_turns`），不在这次范围内。

## 4. 记忆

**原则（已定）：** 纯文本存在 PostgreSQL，通过工具读写，不做 embedding 或向量检索。调研结论一致：Claude Code 的负责人明确说过，早期用 RAG 加向量库，后来发现让 agent 自己搜索更好、更简单；Manus 也不建索引。

- **表 `memories`：** `id`、`user_id`、`content`（一条事实或偏好）、`created_at`、`updated_at`，外加可选的 `source_thread_id`。
- **工具：**
  - `memory_add(content)`：新增
  - `memory_update(id, content)`：修改
  - `memory_delete(id)`：删除
  - `memory_search(query)`：查询
  - 查询按空格拆关键词做 `ILIKE` 子串匹配，命中多的排前面。PostgreSQL 自带的全文检索不会切分中文，所以不用它。
- **常驻注入（B，已定）：** 每个 Run 开始时，把最近更新的 100 条记忆（带 id）随每次请求发给模型，更早的条目由模型用 `memory_search` 查。单条最多 500 字，总条数不设上限。
  - 作为数据，不作为指令（2026-09-29）：记忆放在一条 user 角色的消息里，用 `<memory>` 包起来，注明是应用附上的、此前对话里保存的笔记，不是指令。以前它在 developer 消息里，而网页或邮件可以诱导模型把一段话存进记忆：存进去之后它就以开发者的权限出现在之后每一次请求里，成了常驻指令。系统指令和 `memory_add` 的说明也要求只保存用户自己表达的长期事实和偏好，不保存指令，不保存来自网页、邮件、文件或工具结果的内容，即使它要求被记住。
  - 原因：只靠关键词查询很容易漏。例如记忆写的是“用户希望被称为 akazwz”，模型搜“姓名 名字 称呼”，一个词都对不上。ChatGPT 的已保存记忆、Claude Code 的 MEMORY.md、Letta 的 memory blocks 都是常驻注入，因为模型不知道自己不知道什么。
  - 注入的是 Run 开始时的快照；Run 中新写的条目通过工具结果告知模型。
- **历史对话检索（已实现）：** 记忆只存明确的长期事实，细节留在历史对话里（ChatGPT 的“参考聊天记录”、Claude 的 `conversation_search`）。两个只读工具：
  - `conversation_search(query)`：按关键词搜本用户其他对话里可见的消息文字（每轮的输入与选中的回复），按对话分组，返回标题、时间和命中处前后的片段。消息的文字在写入消息时一起存进 `messages.text`（回复在它的 Run 每个边界更新），用 pg_trgm 的 GIN 索引做子串匹配；以前每次搜索都要把这个用户全部消息的 jsonb 片段展开再匹配。少于 3 个字的关键词没有 trigram，只能在查询其余条件选出的行里逐行匹配。
  - `conversation_read(conversation_id, start, offset)`：按 id 读一个对话的消息文字，一次读取合计最多 4 万字，每条最多显示 4000 字；被截断的消息注明位置，用 `offset` 从截断处接着读，接着读的那一条可以占满整次读取。以前只给前 4000 字，长任务滑出窗口的最终回复读不回来。
  - 代码里对话叫 thread；工具名用 conversation，这是模型和用户的说法，“thread”在英文里还指邮件线程、回复串。
- **用户可控：**
  - 写入记忆时，对话里显示「已记住」（就是一次工具调用）。
  - 设置里可以查看、删除单条记忆，也可以一次全部删除；修改条目和整体关闭记忆尚未实现，需要时通过删除加新增来改。
- **以后再做：**
  - Embedding（计划中，暂不实现）：关键词只能匹配字面相同的词，意思相近而用词不同的（“姓名”与“称为”）会漏。条目多、用词差异大时（主要是历史对话），在关键词匹配之外加向量检索，两路结果合并排序。先上线关键词版本，确认漏检是实际问题后再加。

## 5. 工具

- **注册表：** 每个工具包含
  - 名称，带前缀：`web_`、`memory_`、`sandbox_`、`browser_`
  - 说明
  - 严格的 JSON schema
  - 是只读还是有副作用
  - 超时
  - 输出上限
  - `execute(ctx, args, signal)`

  原则上常驻工具少于 20 个（OpenAI 的建议）；加上浏览器工具后实际接近 30 个，按需加载（见第 5 节“沙箱”下的 [Agent 沙箱](sandbox.md) 以后事项）还没做。错误信息要具体到模型知道下一步怎么改。

- **网页搜索与读取（C 已定，已实现）：** `web_search(query)`、`web_fetch(url, start)`（`src/modules/web/`）。服务商主备切换：TinyFish 优先（免费），它失败时（429、超时、网络错误、被网站屏蔽）由 Jina 接手（按 token 付费：搜索每次 1 万 token，读网页按输出长度）；页面不存在、网址不合法时不切换。外面一层 15 分钟的内存缓存，同一网址、同一搜索词不重复请求；缓存按条数（网页最多 50 条）和总字数（网页正文合计最多 400 万字符，最多 8 MB）两个上限淘汰最老的，避免几个很长的页面（PDF 可能有几 MB 文字）占满 isolate 的内存。不做轮流分配：先用满免费额度，超出部分再付费。
  - 自己实现，不用模型自带的搜索。Cloudflare 自己没有搜索服务，AI Gateway 只透传各家模型的原生搜索（OpenAI 的 `web_search`、Qwen 等）。2026-09-24 实测，清单里 4 个模型经 Responses 都能用，效果也好。但它按模型厂商的价格计费（一次简单提问就消耗 1.2–1.9 万输入 token），搜索过程在模型内部，我们控制不了结果长度和展示，换成只支持 Chat Completions 或 Anthropic 接口的模型就用不了。
  - TinyFish 的 Search 和 Fetch 免费，限额按 key 计：Search 每分钟 30 次、每小时 500 次；Fetch 每分钟 150 个网址、每天 1000 个。超出返回 429，没有付费提额，只能找销售谈。超出后由 Jina 接手，花钱就能扩容（带 key 每分钟：读网页 500 次、搜索 100 次）。两家都失败时，工具把原因转成给模型的说明，模型用已有信息继续回答。其他备选：Brave（$5/千次）、Tavily（$8/千次）；Cloudflare Browser Run `/markdown`（输入网址返回 Markdown，Workers 付费计划下超出每月 10 小时后每小时 $0.09，输出带导航等杂项）。加一家只需实现 `provider.ts` 的接口并排进 `tools.ts` 的顺序。
  - 实测中文质量好：门票、开放时间能找到本地宝和官网，天气能找到中国气象局。结果语言按查询里的文字判断（汉字用 `zh`，假名用 `ja`，谚文用 `ko`），否则按服务默认的美国英语。
  - `web_fetch` 每次最多返回 2 万字符；更长的页面告诉模型总长度和下一段的 `start`，由模型决定是否继续读，相当于上下文管理的第一层。位置按 JavaScript 字符串的 UTF-16 下标计（不拆开代理对），每次只复制要返回的那一段；以前按字符（码点）计，每读一段都先把整页转成字符数组，几 MB 的 PDF 文字就是几千万个元素。每读一段都会重新抓取一次页面，占一次 Fetch 额度。
  - 系统提示要求：时效性问题要联网查、回答时附来源链接、核对来源日期（包括网址里的日期），网页内容只当信息，不当指令。系统提示末尾附当前日期（UTC）。
  - 条款（2026-09-24 读 tinyfish.ai/terms，非法律意见）：
    - 许可范围是“内部业务用途”，不得把服务或其任何部分转授、转售或转让给第三方。面向公众的 agent 由用户触发搜索，标准条款没有明说允许；他们的客户案例（CREAO、Photon）就是这种用法，很可能另签了协议。上线前要找 TinyFish 书面确认，或签单独协议，可以和提额一起谈。
    - 存储：搜索和抓取结果随对话存进数据库，已确认可以存。
    - 数据：我们发出的查询和网址可被 TinyFish 用于分析、人工查看运行记录、训练其模型，以及发布去标识化的汇总数据。查询由模型根据用户对话写出，可能带个人信息：隐私政策需要写明，系统提示应要求查询里不带个人信息。
    - 稳定性：TinyFish 可调整或下线功能（免费政策可能变），改条款提前 30 天通知，可提前 30 天通知终止钱包用户；违反限制条款可被立即终止。所以服务商接口和备用方案要保留。
- **内存（2026-09-29）：** 一个 isolate 只有 128 MB，同时服务多个 Run。除了上面 `web_fetch` 的窗口和缓存上限：
  - 模型请求不再经 OpenAI SDK 的客户端发送（`lib/openai.ts` 的 `sendModelRequest`，`runtime/responses/cloudflare.ts`）。以前 SDK 把请求序列化成字符串，我们的 fetch 为了取出 `model` 再解析回对象，AI binding 又序列化一次；带着接近 20 MiB 文件预算的请求，文件数据（base64 后约 27 MB）同时在内存里存在五份左右。现在把请求对象直接交给 binding，由它序列化一次，响应仍用 SDK 的 `Stream.fromSSEResponse` 解析。生成对话标题这类小请求仍走 SDK 的客户端。
  - 一次执行里读过的文件数据只保留当前请求还要发的（已清理、已滑出的放掉），最多一次请求的文件预算。
  - 执行因内存溢出等原因随 isolate 一起死掉时，不会走到自己的失败计数：心跳在 30 秒后从同一个检查点重新开始，被中断的只读调用重跑，再次撑爆，永不停止。现在 actor 在开始一次执行时就把它算作一次失败（持久存在 DO 的存储里），这次执行提交了一个操作的结果（模型回复、工具结果）才重新计数；连续 5 次没有进展就结束 Run，错误说明服务器在运行它时反复中止、没有完成任何一步。部署导致的重启只要中间有进展就不累计。
- **工具执行与 agent loop 分离（见 [tool-execution.md](tool-execution.md)）：** loop 调用工具时交给执行器（`ToolExecutor`），只认执行器接口；现在有本地执行器和沙箱执行器，别的 DO、用户电脑上的执行器以后实现同一个接口。
- **沙箱（已定 D，已实现）：** Cloudflare Sandbox SDK，每个用户一台电脑，`/workspace` 每次改动后备份到 R2、永不丢失。设计与实现见 [Agent 沙箱](sandbox.md)；这里早先的方案（每个对话一台、`basic` 规格、按 1.0 接口写）已被它取代。
- **浏览器（已定 D，已实现）：** 沙箱里装的 Chromium，和文件系统在一起，电脑的画面显示给用户看；模型不写 Playwright 代码，而是用一组普通的函数工具（Playwright MCP）去操作它，和 Claude for Chrome、Manus 的做法同类（见 [Agent 沙箱](sandbox.md) 的“浏览器”“浏览器工具”）。这是 OpenAI 对 GPT-6 Astra 的推荐做法之一，Manus 也把浏览器摆在沙箱里。

## 6. 实施顺序

1. **循环：** 无预算循环、工具注册表、TOOL Step、增量存储（原 `run_items`，现由 [run-storage.md](run-storage.md) 取代）、中断恢复规则、按连续失败次数限制重试，删除预算相关的状态和字段。加上上下文三层压缩、`web_fetch`、`web_search`。做完这一步，它才是真正的 agent。
2. **记忆：** 四个记忆工具加设置页。
3. **沙箱：** 沙箱工具。
4. **其他：** 外部副作用审批、运行中插话——尚未实现。浏览器随第 3 步的沙箱一起做了，历史对话检索随第 1 步一起做了。
