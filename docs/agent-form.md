# 产品形态调研：常驻 agent（2026-10-02）

用户提出：Grok Bot、OpenAI dots、Meta Muse、Manus Cue 这一批新产品是一种新的形态，Heveta 应该也改成这种形态。本文记录调研结果、Heveta 与它的差距，以及改造方案。

状态（2026-10-03）：用户确认按下面的顺序改，由 Claude 自行推进。第一步里的“主对话”和第二步“审批”的第一版（发邮件先问）已实现，都未上线（见“进度”）；其余未做。

## 这类产品的共同形态

1. **agent 是一个“谁”，不是一个输入框。** 有名字、形象，一条一直延续的对话（Muse 明确分成主对话和 side chat）。dots 的主界面像即时通讯：顶部是形象和名字，时间居中（“Today 9:41 AM”），双方都是气泡，输入框只有一行（“Send message”，加号、麦克风、发送）。
2. **一直在线。** 对话之间它继续干活；可以定时、按条件触发，也可以自己决定什么时候暂停、什么时候醒来继续；有进展、有问题、需要你决定时主动来找你。
3. **有自己的电脑，看得见、接得过来。** dots：“Alfred's computer”卡片里是浏览器画面，底部一条“Alfred has control · Take over”，接管后“Return control”。
4. **活动视图代替对话列表。** dots 的资料页里 Activity 分 In progress / Scheduled / Completed，点开一项看进度、文件、结果和等你输入的请求。后台任务是独立的线程，主对话照常聊。
5. **权限与审批是产品的一部分。** dots 的每类操作四选一：直接做 / 你在指令里明说过才做 / 做之前问 / 交给你做；敏感操作（改密码）永远留给人；网站登录是对话里的一张请求卡，凭据在私密表单里填，不进对话，也可以“接管去登录”。
6. **记忆可见、可延续**，跨对话、跨渠道。
7. **连接**：应用和插件、消息渠道、你自己的电脑（dots：“Its computer and yours”，一次只能连一台）；Cue 更进一步，agent 有自己的邮箱、电话和钱包，以自己的身份对外。
8. **交付的是成品**（文档、表格、网站），不是一段回复。

## 改造方案

原则：先改形态，再加能力；每一步都能单独上线，不做兼容层。

### 第一步：形态（以前端为主）

- **主页就是和 agent 的对话。** 打开就是那条延续的对话，不再是“新对话”空白页。agent 有名字（默认 Heveta，可改）和形象（现有的 H 标志；不做 dots 那种可换装的卡通形象）。
- **其余对话是旁支，不是并列的入口。** 现有的 Thread → Turn → Run 模型不变：主对话是一个特殊的 Thread，其余 Thread 是旁支对话（Muse 的 side chat），仍叫“对话”，不叫“任务”（界面用词保持中性）。侧栏的“活动”（进行中 / 已安排 / 已完成）等第三步有了定时和后台任务再做：现在只有用户发消息时才运行，“进行中”就是对话行上的转圈，单独做一个视图没有内容可放。
- **电脑改成“它的电脑”。** 标题带上名字，底部明确“Heveta 正在操作 · 接管”与“交还”，替换现在的“只看 / 操作”分段开关。
- **输入框收成一行。** 模型、运行位置这些设置收进“+”菜单或 agent 的资料页，输入框只留加号和发送，和这类产品一致。

### 第二步：审批（服务端 + 前端）

对应遗留项 S1。按 dots 的做法：操作分级，对外有后果的（发邮件、在已登录的网站上提交、在用户的 Mac 上执行）默认先问；审批是对话里的一张卡片，Run 挂起等答复。没有这一步，不做第三步。

### 第三步：常驻

- 定时与周期任务（“已安排”），Durable Object alarm 驱动，到点创建 Run。
- agent 可以给自己安排下一次唤醒。
- 主动消息：完成、遇到问题、需要决定时发到主对话，并通过邮箱（已有）通知用户；Telegram 渠道按原规划接入。

### 之后

连接第三方应用、成品交付（文档 / 表格 / 网页）、多个 agent。都是独立的大项，等前三步站稳再排。

## 重新推导：应用围着 agent 组织（2026-10-03）

用户看过“主对话 + 发邮件先问”之后指出：这等于没动——骨架还是“对话列表 + 输入框”的聊天应用，只是多了一个入口。回到参考产品再看一遍（dots 官方页面的界面截图，Muse 的上手评测），它们和聊天应用的差别不在某个功能，而在应用是围着什么组织的：

|              | 聊天应用（Heveta 之前）                  | dots / Muse / Cue                                                    |
| ------------ | ---------------------------------------- | -------------------------------------------------------------------- |
| 打开看到的   | 一个空的输入框，旁边是历史对话           | 一个“谁”：形象、名字、状态，和它的那条对话                           |
| 导航         | 新对话、搜索、历史对话；工具是并列的页面 | 它的对话、它在做什么（进行中 / 已安排 / 完成）、它的电脑、它记得什么 |
| 工作何时发生 | 你发消息时                               | 也在两次对话之间：定时、被事件唤醒、自己安排下一次                   |
| 它找你       | 不会                                     | 做完、卡住、需要你决定时发消息；审批和“请你来登录”是对话里的请求卡   |
| 电脑         | 一个工具页面                             | “Alfred's computer”：谁在操作写在画面上，一键接管，做完交还          |
| 模型、参数   | 每条消息旁边选                           | agent 的设置                                                         |

由此定下 Heveta 的结构——一个人有一个 agent，应用是和它相处的地方：

1. **它是谁**：侧栏顶部是它的名字和状态（空闲 / 工作中 / 等你）；主对话的开头是它的形象和名字；输入框写的是“给 Heveta 发消息”。
2. **导航是它的东西，不是工具清单**：对话（主对话）、电脑（一个地方，屏幕 / 终端 / 文件是标签页）、邮箱、记忆（从设置里拿出来，它记得什么是它的一部分）。之后加“活动”（进行中 / 已安排 / 完成 / 等你）。
3. **旁支对话降为次要**：侧栏下方的一个分组，“新对话”和“搜索”是这个分组的两个按钮。
4. **它自己会动**（最关键的一步，未做）：定时与周期任务、自己安排下一次唤醒、做完或需要你时主动在主对话里发消息并通知你。有了它，“活动”才有内容。
5. **它的电脑可以接管**（未做）：画面上写明谁在操作；接管时 agent 的电脑操作停下等“交还”，和审批是同一个“停下等人”的机制。
6. **模型和运行位置是它的设置**（未做）：从输入框移到 agent 的设置里，输入框只剩加号和发送。

## 进度

### 主对话（2026-10-03，已实现，未上线）

- 每个账号有一个主对话：`threads.main`，每个用户至多一行（部分唯一索引 `threads_user_main_idx`）。`ThreadService.GetMainThread` 第一次读时创建；两台设备同时读只会有一个。它没有标题（界面显示产品名，模型的对话搜索工具里叫“Main conversation”），不能改名、不能删除，不出现在 `ListThreads`（侧栏的“最近”和搜索）里。
- Web：`/` 是主对话，`/new` 是新的旁支对话，`/threads/:id` 不变。侧栏第一项“主对话”，其下“新对话”。主对话是哪一个还没读到时页面显示加载、输入框不可用：否则打的字会进一个新对话。Electron 的“新对话”菜单（⌘N）改到 `/new`。
- 现有的对话原样保留为旁支对话；老账号的主对话在第一次打开时创建，是空的。
- 上线需要先在生产库执行迁移 `20261003065515_main_thread`（加一列和一个索引，旧版本代码不受影响），再部署。没有用户明确同意不执行。

### 审批第一版（2026-10-03，已实现，未上线）

设计、范围和验证见 [approvals.md](approvals.md)。agent 要发邮件时停下，对话里出现一张卡片（收件人、主题、正文，“发送 / 不发送”），答复后从原处继续。等多久都可以，等待期间不占资源。没有数据库迁移，可以和主对话一起上线。

### 骨架改造（2026-10-03，已实现，未上线）

上面第 1–3 点：侧栏顶部是 agent 和它的状态；导航是 对话 / 电脑 / 邮箱 / 记忆；电脑的屏幕、终端、文件合成一个带标签页的地方（地址不变）；记忆从设置移到 `/memory`；旁支对话是侧栏下方的分组，带“搜索”和“新对话”两个按钮；主对话开头显示 agent 的形象和名字。只改了 Web，没有服务端改动。

### 下一步：它自己会动（设计，未实现）

这是和聊天应用真正分开的一步，按下面的方式做：

- **原语是“唤醒”**，不是固定的日程表：到某个时间，带着一句“要做什么”把 agent 叫起来。可以重复（每 N 分钟 / 小时 / 天 / 周 / 月，按 UTC 从上一次的到期时间推算）。agent 用工具自己建、看、删（`schedule_create` / `schedule_list` / `schedule_delete`），所以“明天早上提醒我”“每周一汇总邮箱”“两小时后再看一眼价格”都是同一件事；用户也可以在“活动”页里看和删。
- **每个安排有自己的对话**：到期时在它自己的旁支对话里开一轮（dots 的做法：后台任务是独立的线程，主对话照常聊），不和主对话抢“同一对话只有一个活动 Run”。这一轮的输入不是用户打的字，消息上要标明来自哪个安排，界面按“安排触发”显示，不显示成用户气泡。
- **到点由 Durable Object 的 alarm 触发**，一个安排一个对象：到期 → 开一轮 → 算下一次 → 重新设 alarm。不用扫表的 cron。到期时那条对话上一轮还没结束就顺延。
- **“活动”页**：进行中（正在回复的对话）、已安排（下次时间、周期、删除）、最近完成。侧栏的状态从“空闲 / 工作中”加上“等你”（有调用在等同意），这需要把“等待”写到 PostgreSQL 的 Run 上，侧栏和通知才能在不打开对话时知道。
- **它来找你**：安排的一轮结束、或停下等你时，给用户的登录邮箱发一封通知（受现有的邮件预算约束），之后接 Telegram。
- **前提**：后台运行时没人看着，所以对外的操作必须先问（审批已有第一版；用户 Mac 上的命令在安排里默认不可用）。

### 早先的判断，已被上面的重新推导取代

- agent 的名字（默认 Heveta，可改）和形象：等身份真的有用处（多个 agent、站外渠道里的署名）时再做。
- 电脑改成“它的电脑”：谁在操作、接管与交还。不单独改文案——现在的“只看 / 操作”只是本地开关，agent 不会因为用户在操作而停下；它和审批是同一个机制（agent 请用户来做一件事，停下等“交还”），放在审批之后做，见 approvals.md。
- 输入框收成一行：不做。现在的输入框（加号、运行位置、模型、发送）和 ChatGPT / Claude 的一致，已经够简。

## 定下来的事

1. 主页是一条延续的对话（用户 2026-10-03 确认形态）。
2. 顺序按一、二、三：形态 → 审批 → 常驻。没有审批不做常驻。
3. agent 默认叫 Heveta；是否可改名在做身份时定。
