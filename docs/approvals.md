# 审批：对外有后果的操作先问人

状态（2026-10-03）：第一版已实现（`email_send` 先问），未上线；没有数据库迁移。验证范围见文末。对应审查遗留项 S1（高风险工具没有确认）和产品形态的第二步（[agent-form.md](agent-form.md)）。它也是第三步“常驻”的前提：agent 能在用户不在场时自己跑之前，必须有一处让它停下来等人。

## 要解决的事

现在 agent 的每个工具调用都直接执行。其中有的做了就收不回：发邮件（`email_send`）以 agent 邮箱的身份对外发信；在已登录的网站上提交；在用户自己的 Mac 上执行命令。网页或邮件里的内容可以诱导模型去做这些事（S1）。

同类产品的做法（见 agent-form.md）：dots 把每类操作分成“直接做 / 指令里明说过才做 / 做之前问 / 交给你做”；Muse 有一个待审批队列；Cue 是预算加“不可撤销的事先问人”。共同点是：**审批是对话里的一张卡片，agent 停下来等答复，答复后从停下的地方继续。**

## 做法

### 一次调用停下来等人

不新增 Run 状态。等人答复的是**一次工具调用**，不是整个 Run：Step 已经有 PENDING（“已登记、未发出”），等待同意的调用就停在这里。Run 仍是 RUNNING（未结束、归它的 actor 管），“同一 Thread 最多一个活动 Run”“侧栏的进行中标记”“停止”都照旧成立，`unfinishedRun` 的两个部分索引不用动。

- **工具声明**：`ToolSpec.consent: boolean`——这个工具的调用要先得到用户同意。必须同时是非只读、不可并行的（只读调用没有后果；并行组里夹一个要等人的调用，顺序规则就说不清）。
- **checkpoint**：`PendingToolCall.consent?: "requested" | "granted" | "refused"`，随工具 Step 一起保存（`StepUpdate.consent`；待答的调用本来就是从本地的 Step 记录还原的）。字段是可选的，checkpoint 版本不变，部署时正在跑的 Run 不受影响。
- **loop**（`runtime/loop.ts` 的 `answer`）：轮到一个需要同意、还没有答复的调用时，把它标成 `requested`，发出 `consentRequest` 事件（对话里的调用变成一张待答复的卡片），保存 `tools` 边界，然后 loop 以 `StopReason.WAITING` 返回。它之前的调用已经按顺序答完；它之后的调用等它。恢复（`tools` 阶段）时：`granted` 的照常开始执行；`refused` 的不执行，模型读到的结果是“用户没有同意这次操作；除非用户再提出，不要重试”；还是 `requested` 的，loop 再次以 WAITING 返回。
- **driver**：loop 以 WAITING 返回时不写终态，这次执行正常结束；工具按“Run 还会继续”释放（`close(false)`：连接放掉，电脑的租约留着）。
- **actor**：执行以“等待”结束时，不归档、不退役，把失败计数清零并**取消闹钟**：等人的 Run 不需要心跳，Durable Object 休眠，不占资源。等多久都可以；存储里的 checkpoint 就是它的全部状态。
- **答复**：`RunService.AnswerToolCall(run_id, tool_call_id, approved)` → actor 的 `answer`。actor 先等正在收尾的执行结束（checkpoint 里有 `requested` 的调用时，loop 已经在返回的路上），再用一次普通的 `RunBatch` 提交把该调用标成 `granted` / `refused`（同时更新对话里那张卡片），然后安排立即唤醒。同一个答复重发没有效果（以对话里那次调用已记录的答复为准，Run 继续甚至结束之后重发也成立）；已经答过再给相反的答复、或调用不在等待中（Run 已结束、被停止），返回 FailedPrecondition。记录答复的逻辑在 `runs/consent.ts`，actor 只负责串行和唤醒。
- **停止**：和现在一样。CancelRun 提交后唤醒 actor，这次执行发现已取消，在开始任何调用之前结束 Run；等待中的调用没有开始过，不需要收集结果。
- **竞态**：答复到达时执行可能还没完全结束（checkpoint 已保存、事件已发出，但 `#execute` 还没走到取消闹钟）。执行结束后在一次存储事务里重新看 checkpoint：还有 `requested` 的调用才取消闹钟，否则立即安排下一次唤醒。

### 对话里的样子

- 输出消息的 `ToolCall` part 增加 `consent`（未指定 / 等待 / 已同意 / 未同意）。等待中的调用不收进“N 个步骤”的折叠块，而是单独一张卡片，在回复里它发生的位置：做什么（发邮件：收件人、主题、正文、附件），两个按钮“同意”“不同意”。答复之后卡片收起成普通的一步。Run 被停止或已结束时不显示卡片（没有可答的了），那次调用显示为没有执行的一步。
- 按钮按下到服务端状态回来之间，用“进行中的命令”覆盖显示（和发送、停止一样，见 `apps/web/AGENTS.md` 的状态模型），失败则恢复按钮并提示。
- 输入框保持“正在回复、可停止”的状态：Run 没有结束。
- 多端：卡片是消息的一部分，任何一台设备都能答；先到的生效。

### 哪些调用要问（第一版）

只有 `email_send`。它是现在唯一“对外、发出就收不回”的工具，也是 S1 点名的那个。机制对所有执行器通用（声明在 `ToolSpec` 上），其余的按下面的顺序加，每加一类都要有对应的规则，否则会问得太多：

| 操作                              | 第一版 | 之后                                                                                                   |
| --------------------------------- | ------ | ------------------------------------------------------------------------------------------------------ |
| 发邮件                            | 先问   | 规则：对某个收件人“以后不用问”                                                                         |
| 在用户的 Mac 上执行命令、操作界面 | 不问   | 需要“这次对话里都允许”的规则才可用，否则每条命令都弹；和设备的“允许访问”开关一起设计                   |
| 浏览器里提交表单、付款、登录      | 不问   | 浏览器工具分不出“提交”和“点击”；要么让模型在提交前调用一个“请用户确认”的工具，要么交给用户接管（见下） |
| 记忆写入                          | 不问   | S1 已用“引用数据 + 不是指令”缓解                                                                       |

### 接管与交还（下一步，同一个机制）

dots 的“网站登录是对话里的一张请求卡，也可以接管去登录”和这里是同一件事：agent 调用一个“请用户来做”的工具（比如登录、过验证码），调用停在等待，用户在电脑页接管、做完、点“交还”，就是这次调用的答复。所以电脑页的“谁在操作 · 接管 / 交还”放在这个机制之后做，不单独改文案：现在的“只看 / 操作”只是本地开关，agent 并不会因为用户在操作而停下，写成“Heveta 正在操作”是不实的。

### 用户不在场（第三步用到）

调用进入等待时，driver 已经在这个边界上：第三步在这里加一条通知（邮件，之后是 Telegram）。等待不超时；长期没人答复的 Run 一直占着它的对话，由用户停止。

## 不做的

- 不做四档可配置的权限表。先有一类真实的操作和它的规则，再加第二类。
- 不做独立的“待审批队列”页面。只有一种会等待的操作时，卡片在对话里就够了；第三步有了后台任务再做活动 / 待办视图。
- 不让模型自己决定要不要问（除了上面说的“请用户确认 / 请用户来做”工具）：是否需要同意由工具声明决定，模型绕不过去。

没有数据库迁移：状态都在 actor 的本地存储和消息 part 里。

## 验证（2026-10-03）

- loop 单元测试：需要同意的调用在它之前的调用答完后停下、不执行；带着“同意”恢复只执行一次；“不同意”不执行、模型读到说明；没有答复时继续等待且不重复保存。
- PostgreSQL 集成测试（driver、本地存储、`recordConsent`、RPC；不模拟 Durable Object）：等待时 Run 仍是活动的、Step 为 PENDING；同意后执行一次并完成；同一答复重发成立；相反的答复、停止后的答复被拒；不同意则不执行；等待中停止以 CANCELLED 结束；别人的 Run 返回 NotFound。
- 本地真实运行（`pnpm dev`，真实 RunActor 和模型）：让 agent 发邮件，出现卡片；刷新页面、换深色和手机宽度后仍在等待；点“不发送”，模型回复没有发送。浅色、深色、手机宽度截图核对过。
- 没有验证：真实环境里“同意”后的实际发信（本地只走了“不发送”，同意的路径由集成测试覆盖）；actor 里答复 / 停止与执行收尾之间的竞态（按代码推演，没有能稳定复现的测试）；等待数小时后恢复；多台设备同时答复。
