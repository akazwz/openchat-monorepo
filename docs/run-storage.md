# Run 增量存储设计

状态（2026-09-30）：已实现、本地验证并完成生产数据库迁移和 Cloudflare 部署。按绿地开发处理，不保留旧历史或旧存储兼容分支。本文处理系统检查中的 P1：长任务反复读写整条助手消息，以及变化后的整份模型上下文。领域定义和外部框架对照见 [agent-model.md](agent-model.md)；[agent-runtime.md](agent-runtime.md) 与 [sync.md](sync.md) 已同步实际存储与读取边界。

## 1. 结论与范围

保留 Thread → Turn → Run → Step 的业务关系。继续使用每个 Run 一个 RunActor，由它的内存聚合短暂输出、SQLite 持久化运行中的增量与恢复状态；PostgreSQL 保存受理记录、控制命令、文件引用和定稿后的历史。UserHub 继续只转发通知，R2 继续保存文件内容。无需新增 Redis。

本次设计同时处理提交、恢复、归档、读取、取消、删除、文件清理和部署交接，不改变模型结果未知时的恢复策略，不增加运行中插话、分支、子 agent、工具审批、账号配额或图片处理。

设计目标是让每批新内容的保存量取决于本批新增量，避免反复序列化、读取、比较和写回累计正文。一次归档仍需完整保存该尝试的公开内容，但按片段和数据块传输，避免在归档时重新组装一份巨大的 JSON。

## 2. 领域身份与保存时机

```text
Thread：一段对话
└── Turn：一次已受理输入
    ├── 用户 Message：这份输入
    └── Run[]：针对输入的不同回复尝试
        ├── RunStep[]：模型请求／工具调用
        ├── 助手 Message：本次尝试的全部公开内容
        │   └── MessagePart[]：文字、摘要、调用、结果、文件
        └── LoopCheckpoint：本次尝试的私有恢复位置
```

Message 从受理时就有稳定身份；正文在 Run 结束时定稿。归档沿用原 runId、messageId、partId 和 Step 身份。一个工具完成、一个文字片段完成、一次提交成功，都不会新建“历史 Message”。正常完成、取消收尾、失败终止都会归档该尝试的已提交内容；可恢复的中断仍使用原 Run。

| 数据                                                                        | 权威保存位置 | 保存时间与保证                                         |
| --------------------------------------------------------------------------- | ------------ | ------------------------------------------------------ |
| Thread、Turn、用户 Message、Run 身份、助手 Message 占位记录、requestId 指纹 | PostgreSQL   | 受理事务提交后才确认发送成功；附件同时登记引用         |
| 尚未提交的流增量、解析器临时状态、可以重建的缓存                            | DO 内存      | 短暂聚合；进程消失时可能丢失；不作为已确认公开进度推送 |
| 已提交的助手输出、活跃 Run 的公开快照和 revision                            | DO SQLite    | 每个进度批次可靠提交后可补读、推送                     |
| 操作意图、Step、完整取得的操作结果、原生模型项、恢复位置                    | DO SQLite    | 调用前保存意图；结果保存后才进行下一项操作             |
| 取消意图、请求撤回、Thread 删除、文件引用与文件状态                         | PostgreSQL   | 对应命令确认前提交；通知失败可重试，不依赖进程内存     |
| 定稿的公开片段、最终 Run 和 Step、历史文本索引                              | PostgreSQL   | 结束后的归档交接确认完成后成为历史读取来源             |
| 文件正文                                                                    | R2           | 按现有上传与清理流程保存；DO 和 PostgreSQL 只保存引用  |

初始化前的 QUEUED、归档后的终态可从 PostgreSQL 读取；运行中的公开版本由 DO 提供。PostgreSQL 的活动 Run 行承担查找、鉴权、限制同一 Thread 同时一个活动 Run、保存控制命令等职责，不被当作完整实时快照。

## 3. 版本与单一提交者

各标识分别解决不同问题：

| 标识                   | 含义                                                           |
| ---------------------- | -------------------------------------------------------------- |
| `attempt`              | 同一 Turn 下第几次回复尝试；用户重新生成时增加                 |
| `stepIndex`            | Run 内登记操作的顺序；恢复沿用，新的实际模型请求使用新的 index |
| `partId`／`ordinal`    | 助手 Message 内片段身份／展示顺序                              |
| `batchId`／`commitSeq` | 存储批次去重身份／提交顺序；私有提交也占提交位置               |
| `revision`             | 公开 Run 或输出变化的版本；纯私有检查点提交不增加              |
| `epoch`／`itemSeq`     | 私有上下文的一份基底及其后追加项的位置                         |
| `sealId`               | 一次已冻结归档内容的身份；重试归档沿用它                       |

受理事务建立公开 revision 1。DO 初始化采用这份固定的受理快照；初始化之前执行器不调用模型或工具。之后该 Run 的所有公开 revision 都由同一个 DO 提交入口分配，包括领取执行、输出和已观察到的取消意图。PostgreSQL 的 Cancel 命令只持久化控制意图，不再独立增加公开 revision。

执行开始时，DO 提交 RUNNING 与 startedAt，再向 PostgreSQL 写一次小的状态投影。投影只更新仍活动的原 Run 的状态与开始时间，不覆写取消意图或 revision，不重建不存在的记录。投影失败时从 DO 重试；PG 行保持 QUEUED 仍属于活动 Run，不影响同一 Thread 的唯一活动约束。不得用这个投影覆写 DO 的公开快照。

DO 的公开变化在本地提交后按 revision 顺序通知 UserHub。重复或遗漏通知沿用当前客户端的版本与快照补读规则。不要求 hub 保存完整事件日志；归档终态的投递状态在 DO 持久化，投递失败由 alarm 重试。

## 4. 运行步骤的精确定义

当前工具被模型提出时就登记为 RUNNING，startedAt 是登记时间。新设计明确区分：

| 状态                  | 意义                                                   | 时间字段                                  |
| --------------------- | ------------------------------------------------------ | ----------------------------------------- |
| PENDING（新增，私有） | 已登记操作，尚未提交“即将调用”的意图                   | createdAt 已有，startedAt 为 null         |
| RUNNING               | 已提交调用意图，外部操作可能已经开始，结果尚未可靠记录 | startedAt 在调用前的可靠边界设置          |
| COMPLETED／FAILED     | 已可靠记录成功结果／错误结果                           | finishedAt 设置；未知用量保持 null        |
| CANCELLED             | 操作因停止或本次 Run 结束而不再继续                    | PENDING 可以直接取消，startedAt 仍为 null |
| INTERRUPTED           | 已登记的在途操作结果无法确定，需要保留中断事实         | 不冒充“确定执行失败”                      |

createdAt 是登记时间，startedAt 是提交发出意图的时间，finishedAt 是结果收尾时间；这些是服务端观测时间，不宣称等于外部进程的精确起止时间。Step index 表示登记顺序；只读并发时完成顺序可以不同。

PG 的既有 StepStatus 数值不重排，新增 PENDING 使用新值，约束相应允许 PENDING／RUNNING 没有 finishedAt，PENDING 没有 startedAt。新记录从登记时写 createdAt，调用意图提交时写 startedAt；不回填旧记录或维护历史时间语义。

工具调用先登记 PENDING 与原文参数引用。每次实际调用前，在本地事务中将该 Step 改为 RUNNING，再等待可靠保存，随后才调用执行器。只读并发工具分别登记这一边界。有副作用的操作继续按现有顺序执行。恢复时 PENDING 可首次执行；RUNNING 的有副作用调用先 resume／收集结果，无法收集时报告未知；RUNNING 的只读调用可以重跑。

Step 的 UUID 在首次登记时生成并持久保存，归档使用同一 ID。`StepCheckpoint` 改称 `StepUpdate`，表示一次边界的变更集合；完整步骤记录由 local_steps 持有并归档为 StepRecord。服务端的片段元数据保留归属 stepIndex：文字／摘要属于 MODEL Step，调用／结果／结果文件属于对应 TOOL Step。一项操作可有多个片段，片段正文状态不等于操作状态；产品 MessagePart 和 RPC 继续使用现有字段。

## 5. DO 的数据形状

表名是设计名称，具体迁移随实现生成；不将下列存储表变成新的产品实体。

| 本地数据                                                       | 保存内容                                                                               | 写入粒度                                         |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `local_state` 与 KV `run-schedule`                             | 身份、公开状态、revision、commitSeq、checkpoint 游标、调度信息、内部生命周期、归档位置 | 小记录更新                                       |
| `local_batches`／`batch_parts`／`batch_changes`／`batch_steps` | batchId、内容摘要、提交位置、待处理依赖；用于确认一次重试是否已提交                    | 每批一次小记录                                   |
| `local_parts`／`part_heads`                                    | 稳定 partId、ordinal、类型、来源 Step                                                  | 创建一次                                         |
| `part_versions`                                                | 某提交位置的文本元数据、正文 generation 和已提交长度／块位置、结果摘要                 | 追加小记录                                       |
| `part_chunks`                                                  | 文字、摘要、工具原文参数、JSON 工具结果等正文；按 partId、generation、块序号定位       | 追加数据块                                       |
| `local_steps`                                                  | 稳定 ID、index、种类、状态、时间、响应 ID 与已知用量                                   | 登记／发出／取得结果时更新；已收尾操作不重新修改 |
| `native_items`／`native_chunks`                                | 当前 epoch 的原生模型项，含私有加密 reasoning；pending 参数从这里定位                  | 完整项追加；大项分块                             |

checkpoint 只保存 phase、当前 MODEL Step、待答调用的位置、epoch、itemSeq、lastStepIndex、滑出信息和比例等。参数正文和完整 transcript 不放入这个小记录。恢复所需的整个待答列表通过已登记 Step 与原生调用项重建，避免把巨大参数再次塞进 checkpoint。

正文采用 text／JSON 编码，UTF-8 数据块不超过 48 KiB（最多 16,000 个 UTF-16 码元），归档页目标不超过 400 KiB，内部正文 RPC 每页最多 10 块。切割不得破坏字符编码。公开文本增量的偏移使用现有 JavaScript 字符串语义，块和页面按 UTF-8 字节校验大小，正文长度及读取偏移按 UTF-16 码元记录。工具参数保留模型原文，供界面解析的对象不替代它。

Cloudflare 当前 SQLite 的字符串、BLOB 和单行上限为 2 MB，序列化 RPC 上限为 32 MiB，所以完整工具结果、原生项、检查点基底和归档均需分块，不能把“大 JSON 的 key 换个地方”当成实现。[DO 限制](https://developers.cloudflare.com/durable-objects/platform/limits/)、[RPC 限制](https://developers.cloudflare.com/workers/runtime-apis/rpc/#limitations)

公开片段的版本头和正文块在活动 Run 内保留，以便按已提交读取位置取快照。完成正文需要供应商最终快照纠正时，保留同一 partId，建立新的正文 generation，可靠提交后发布片段替换；不把纠正内容当作重复 delta 追加。一般流增量只追加本批文字，完整工具结果只保存一次。

## 6. 提交与内存边界

进度仍按现有约 250ms 或累计 100 次输出更新触发；另对待提交字节设目标上限，避免产生巨大内存批次。输出速度高于保存速度时使用背压，不持续堆积无界 pending 数组。内存只保留当前仍在生成的片段、工作窗口、待提交批次和可重建缓存，不保留整场任务所有工具结果的副本。

一个批次提交过程：

1. 构造稳定 batchId 和本批新增内容。大型结果先分块写入未公开的暂存区域，完成全部块并可靠保存后记录完整的待提交批次；局部写入不能被当作完整结果。
2. 如有新文件，执行第 10 节的 PostgreSQL 引用登记。
3. 在短的本地事务中提交片段版本头、正文可见位置、StepUpdate、原生项可见位置和 checkpoint 游标；需要公开变化时同时分配一个 revision。
4. 等待存储可靠保存，然后允许下一项模型／工具操作，并按序通知 hub。相同 batchId 重放只返回原提交位置；相同 ID 的不同内容拒绝。

SQL 使用 `ctx.storage.transactionSync()` 等官方事务机制，可靠边界完成后才发出网络调用或通知；不使用 allowUnconfirmed 提前确认。必要时用 `storage.sync()` 明确等待待写数据保存。事务内只执行本地操作，不等待 PostgreSQL、模型、工具或 hub。[SQLite 事务与 sync](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactionsync)

序列化的是提交队列，而不是整个执行过程。不得用 blockConcurrencyWhile 把一场长任务和外部 I/O 全部包住，否则读取、取消和工具对当前对话的查询会被挡住。

需要可靠保存的边界包括：初始恢复位置、模型请求前、完整模型响应后、每个工具发出前、每个工具结果、窗口重新建立基底、结束封存。普通未成功提交的流批次可由下一批携带；已经取得完整操作结果时，优先可靠保存待提交结果，重启后先完成该批次，随后再按 checkpoint 恢复，避免把已存的结果误判为未知操作。

## 7. 私有上下文与恢复

首次执行从 PostgreSQL 的历史和本次用户输入建立工作窗口，只保存这一窗口作为 epoch 基底。之后将完整模型输出项、工具调用和工具结果追加进去，checkpoint 更新游标。文件仍只有 ID 引用；请求使用的 data URL 不进入恢复存储。

Thread 的 `context_window` 继续保存在 PostgreSQL：新 Run 组装历史时使用跨轮次切点、工具结果／文件清理边界及 token／字符比例。首次组装使切点移动时仍提交这份小记录，更新比例也不携带正文。当前 Run 中途窗口变动只进入本地 epoch 与 checkpoint，不覆写 Thread 的跨轮次切点，保持现有前缀重建规则。

发生窗口滑动、旧工具结果清理或文件清理时，建立新的 epoch，分块写入变换后的完整窗口；可靠提交新 epoch 指针、滑出信息和 checkpoint 后，才清理旧私有基底。仅在这种边界重建窗口，不在每一步重写累计上下文。公开 Message 的完整记录独立保留，窗口清理不会删掉用户能读取的输出。

窗口的移出单位是上下文段，不是 RunStep。原 `Omitted.steps` 每移出一组模型项及其工具结果只加一；现已改为 `omitted.contextSegments`，窗口提示也使用 context segment，不能把该值当作步骤数或恢复 index。使用新 checkpoint 定义，不保留旧字段解码。

恢复顺序为：核对 PG 控制记录 → 处理已完整暂存的结果／待文件登记批次 → 处理封存归档 → 按 checkpoint 执行循环。内部生命周期优先于 loop phase。

| 恢复位置                              | 行为                                                                                                                                         |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 已受理但 DO 还未初始化                | 从固定的受理身份与用户输入初始化；不丢失已接受发送                                                                                           |
| ready                                 | 从已提交窗口继续下一次模型请求                                                                                                               |
| model，且没有完整取得的待提交模型结果 | 结果未知，沿用现有不重放策略；失败并保留已提交输出                                                                                           |
| tools                                 | 已存结果不重跑；PENDING 首次执行；在途工具按第 4 节收集／重放／报告未知                                                                      |
| 已封存                                | 只继续归档与通知；不再进入模型或工具循环                                                                                                     |
| PG 已终态，DO 尚未确认归档            | 核对 sealId 和归档内容，再确认本地交接                                                                                                       |
| PG Run 不存在                         | 受理前预安排 alarm 的等待期仍沿用现有规则；受理未提交则退役；已初始化 Run 消失则停止执行和公开读取，进入删除清理；禁止由 DO 重建 PG 业务记录 |

运行中连续无进展失败的上限继续为 5 次，提交操作结果才算新进展。结果封存后的归档／通知重试继续退避，跳过执行失败上限处理，不把归档失败变成重新执行任务，或把已完成结果改成失败。

## 8. 定稿与 PostgreSQL 归档

内部保存生命周期为 active → sealed → archived；deleted 可从任意位置进入。它们不进入公开 RunStatus。

sealed 表示该尝试已经停止执行，公开内容、原生结果与候选结束原因被冻结，但 PostgreSQL 归档尚未确认。封存先可靠保存剩余输出，可发布正文的最后一批进度；随后冻结公开 revision，预留下一个 revision 作为终态。此后不再分配新的进度或取消 revision。

公开 COMPLETED／FAILED／CANCELLED 在 PG 最终事务确认后才发布。归档期间仍占用 Thread 的活动 Run 名额，避免界面说可以发下一轮而 PG 仍拒绝它。这延长了归档故障期间的“正在回复”时间，是保持现有受理一致性的明确取舍。

### 分页归档

PostgreSQL 保留用户消息的现有不可变 parts；新的助手消息正文用独立的 `message_parts`、`message_part_chunks` 保存。记录保留 ordinal、类型、来源 Step、文本元数据、工具名称／callId／错误标记／文件引用，以及工具结果序列化字符长度。普通列表可只读元数据和短结果，展开时再读大结果正文。

`run_archives` 是 Run 的私有归档交接记录，保存 sealId、页面计数、记录数和内容摘要；冻结正文及候选结果、最终 revision 和导出游标保存在 DO 的 seal／archive 状态，终态版本最后写入 PG Run。片段、块和步骤按固定顺序分页面导出；每页有序号与内容摘要。使用 runId、sealId、页面序号以及片段／块身份幂等导入，回包丢失时可以确认原页面，不重复插入正文；同一页面身份但内容摘要不一致时拒绝导入。小的归档位置更新与该页数据在 PG 同一事务中提交。

分页导入的数据在 Run 活动期间不可作为历史正文返回，读取路由仍走 DO。最终步骤身份使用 DO 原 ID；正文只导出每个 part 的最终 generation。私有原生模型项和加密 reasoning 不进入历史归档。

### 最终交接

1. DO 已可靠封存全部最终公开内容、步骤记录、候选结束原因、时间及 sealId。
2. 所有归档页成功导入并核对顺序、计数和累计摘要。
3. PG 最终事务锁定 Run：确认归属和交接身份；按当前取消意图裁决最终状态；收尾尚未结束的 Step；由已导入文本块构建 messages.text；调整最终文件引用；写 finishedAt 和 DO 预留的最终 revision，并标记归档提交。
4. DO 取得归档确认，保存完全一致的最终公开状态，发布终态通知；通知丢失则由 alarm 重试。
5. 确认归档与终态通知后清理公开数据块、原生上下文和恢复记录，最后清除 alarm 与本地数据。迟到调用先查询 PG，禁止重新开始终态或已删除的 Run。

整个过程无需跨两个数据库的原子事务：DO 冻结后可重试；PG 暂存不对外成为历史；PG 最终事务切换读取来源。PG 已提交但确认丢失时，查询原 sealId 的终态进行确认，不生成第二条消息或新 Run。

`finishedAt` 使用封存批次中已可靠记录的执行收尾时间；PG 归档失败期间的等待不改写这个时间。未知 token 保持 null。已经可靠记录结果的终态 Step 保持不变；其余 Step 在最终事务中根据封存时的调用事实、候选结束原因和已提交取消意图收尾，PENDING 未发出与 RUNNING 结果未知必须区分。不要提前把所有未收尾步骤冻结为“确定失败”。

## 9. 统一读取边界

建立服务端 Message／Run 读取层，统一 PG 归档和 DO 活动数据。对外继续是现有 RunSnapshot、RunChange、Message 和 GetToolResult。

| 路径                                   | 新读取规则                                                                         |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| StartTurn／RetryTurn 的新受理响应      | 返回 PG 事务建立的 revision 1 和固定消息身份；迟到响应按现有版本规则合并           |
| 同 requestId 重放                      | PG 只确定原 Run；离开受理事务后经统一读取层返回该 Run 当前快照                     |
| GetRun／CancelRun 的快照               | 未初始化的 QUEUED 可读受理快照；活动读取 DO；已归档读取 PG                         |
| ListMessages                           | PG 决定分页、消息身份及每 Turn 的最新尝试；活动助手消息补读 DO；定稿消息读 PG 片段 |
| GetToolResult                          | 核对消息所有权与可见尝试；活动按 callId 读 DO；归档后只读对应 PG 结果块            |
| ListThreads／GetThread／侧栏活动标记   | PG 活动 Run 索引仍决定是否正在回复；归档最终事务后解除活动状态                     |
| 模型开始新 Run 的历史                  | 更早 Turn 的已归档消息由 PG 重建；重新生成排除同 Turn 较早的助手尝试，沿用当前规则 |
| conversation_read／conversation_search | 已归档内容读 PG；活动内容按已提交 DO 文本补读并合并，保留当前含活跃对话的行为      |

DO 的内部读取返回固定 commitSeq／revision 的版本头和可分页读取的正文位置；后续追加不能混进这份快照。跨页时保留其 generation，归档清理抢先发生时由读取层核对 PG 并重新读取归档版本，不返回空消息来冒充成功。

新 Run 重建模型历史时先分页读取片段元数据与长度，按已有窗口和结果清理规则决定保留范围，再读取需要的正文块；大工具结果已经被清理时只构造现有占位说明，不先加载原结果。不能先还原上一场长任务的完整助手 Message，再在内存里滑出大部分内容。助手正文只有片段存储这一条读取路径，不回退读取 messages.parts。

不能在持有 PG 的 Run 行锁或受理事务时等待 DO：DO 可能正在归档并等待同一行。流程是 PG 鉴权与确定来源 → 读取 DO 已提交快照 → PG 复查存在性、可见尝试及归档状态；删除则 NotFound，已归档则从 PG 读取最终版本。若来源持续变化或不可用，返回可重试错误，禁止将旧 PG 占位正文配上新的 DO revision。

列表和 GetRun 的快照统一省略超过现有 2000 序列化字符阈值的工具结果，事件中的结果片段也采用同一规则；继续由 GetToolResult 读取全量。客户端保留／失效按需加载的结果缓存时必须按 messageId、callId 和当前版本核对，不能让省略结果的迟到快照覆盖新尝试。

活动文本检索按数据块进行，保留跨块关键词匹配和片段边界换行；不能仅逐块 LIKE 而漏掉跨块词，也不能遗漏一个活跃 Run 中已滑出模型窗口的文字。PG 历史候选与 DO 活动候选按现有命中分数、消息顺序和对话分组规则合并；重新查询已经归档的候选并按 messageId 去重。当前 Run 的对话工具直接注入本地已提交读取接口，避免对本 DO 发起递归 RPC。其他活动 Run 使用有限并发、分页读取；依赖失败明确报错，不悄悄省略活跃内容。

公开 API 的完整正文大小与浏览器渲染成本仍随可见文字增长。本方案解决累计重写和大工具结果的读取，内部传输可分页，不承诺现有公开 Message 接口能展示任意大小的单条正文。

对话工具沿用 `threads/history.ts` 的 `messageText` 口径：只读取文字片段并以换行连接，不将工具参数、工具结果、推理摘要或文件内容加入检索。PG 最终文本索引和 DO 的活动文本读取必须使用同一投影规则。

## 10. 文件、取消和删除

### 文件引用

现有垃圾回收只看 PG 的 message_files／email_files。活跃 Run 中生成的文件不能等结束归档才登记，否则长任务内仍使用的文件可能被清理。

新文件结果先在 DO 中保存为完整待提交批次，再在 PG 事务中核对 Run 存在和控制意图、锁定可用文件，并引用到受理时创建的助手 Message。引用成功后，DO 才把结果、文件片段与 checkpoint 一起公开提交并进入下一步。失败重试处理这份已存结果，不重新执行产生它的工具。

PG 引用已成功、DO 还未公开就中断时，暂时多保留文件是可接受的；文件还未受保护时不能承诺结果已提交。只出现在私有工作窗口的文件也登记到该助手 Message，DO 记录其依赖来源；活动期间即使窗口清理也保留这些引用，避免为释放引用增加跨存储竞争。归档最终事务按公开片段核对该助手 Message 的引用，释放仅为暂存或私有窗口保留的文件，并按现有规则清理无人引用对象；不删除其他消息／邮件的引用。

### 取消

Cancel 继续先在 PG 保存取消意图；未知 requestId 继续按现有请求锁撤回。随后通知 DO，DO 读取已提交意图、提交公开 cancelRequested，再中止执行器。快照和 revision 由 DO 统一提交。通知未成功时返回可重试错误，PG 意图保留。

执行器每个操作边界核对 PG Run 是否存在、取消意图及终态；现有约 30s 心跳也读取这份小控制记录，作为长命令期间通知丢失的兜底。无法核对时不启动下一项模型或工具操作；已经发出的操作保留其未知结果处理，不宣称可以撤回外部副作用。

完成与停止的裁决保持现有行为：已经取得最终模型回复则 COMPLETED；其他结束候选遇到已提交取消意图则 CANCELLED。封存后 Cancel 不再占用预留终态 revision：协助完成归档并返回确认后的最终快照；暂时无法归档时返回可重试错误，不另行发布一个更高版本的活动快照。

### 删除

Thread 删除事务继续删除 PG 中的 Turn、Run、Message、归档暂存和最终片段，并标记无人引用的文件；取出活动 Run ID 后通知 DO。PG 记录不存在即是删除事实，DO 的晚到归档不得重新创建 Thread／Run／Message。

DO 收到删除通知或心跳／边界读取发现 Run 不存在后，停止执行、清理本地公开与私有数据、清除 alarm。通知丢失由预先存在的 alarm／心跳补做；封存待归档的对象也保持 alarm。已成功归档并清理的对象不再留正文。客户端继续使用已删除 Thread 的终态标记拒绝迟到事件。

DO 本地清理按官方 deleteAll／deleteAlarm 规则处理持久数据与唤醒，完成前不能仅停掉 alarm 留下不可追踪的正文。[存储清理说明](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/#remove-a-durable-objects-storage)

## 11. 实现边界与迁移

| 模块                                                          | 需要统一修改的职责                                                                      |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| runtime/checkpoint、loop、tools、window                       | checkpoint 位置化；StepUpdate；窗口上下文段计数；登记与发出分开；保持模型／工具恢复规则 |
| runs/actor                                                    | 本地存储初始化、控制记录核对、归档／通知／删除唤醒；继续每个 Run 一个 actor             |
| runs/driver、output、commit                                   | 输出改为增量批次；移除整条消息复制比较；本地原子提交与归档交接                          |
| runs/commands、queries、records、turns/service                | 保留 PG 受理与 requestId 去重；Cancel 不独立分配 revision；统一快照读取                 |
| threads/service、history、storage、part-codec、runs/rpc-codec | 列表、详情、对话检索与模型历史统一读取；大结果在存储读取时省略                          |
| files/lifecycle                                               | 活跃结果的引用登记、私有文件保护、归档与删除时释放                                      |
| db/schema 与迁移                                              | 归档交接与片段／块；Step 登记时间和可空 startedAt、PENDING                              |
| web/runs、threads、工具结果缓存                               | 沿用版本合并；核对快照和事件省略大结果时的按需加载行为                                  |

实现顺序是先完成共用的提交与读取边界，然后一起接通 DO 执行、PG 归档、控制命令和文件生命周期。不能只迁 checkpoint，留下完整正文在每次提交中重写；也不能先把写入迁走而 RPC 仍只读 PG。

按绿地开发只保留新执行与读取入口；不增加 storageVersion，不维护旧助手 parts、旧 checkpoint 或新旧 Run 双轨。数据库通过 schema 生成迁移建立新片段与归档结构，移除 PostgreSQL 私有 checkpoint 表。DO 仍使用同一 RunActor 类；保留受理前 armRun、受理事务限时和提交后 dispatchRun 的顺序，先保证已有持久唤醒，再确认发送成功。2026-09-30 按用户授权执行生产迁移并部署：执行前没有活动 Run，移除旧 checkpoint 表，既有账号、对话、附件和邮箱记录保留，旧历史正文不做兼容适配。

## 12. 验收与当前限制

这份设计已沿以下实际路径核对：受理与重复请求、重新生成、模型／工具循环、输出投影、Step 与 checkpoint 提交、RunActor 唤醒、PG 消息列表／详情／对话检索、窗口重建、文件引用与垃圾回收、取消和 Thread 删除。官方资料核对了概念粒度、SQLite 事务、存储和 RPC 限制。

实施时必须覆盖这些具有业务意义的验证。还需用上一 Run 含大量工具结果的对话验证下一条输入和重新生成：新归档数据从元数据确定工作窗口，只读取所需正文，被清理的大结果不先进入内存，检索仍只包含现有文字投影。

| 场景                                              | 必须成立的结果                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------- |
| 长任务 100／1000 个固定大小结果，含流式文字       | 公共／私有新增保存量近似随内容线性增加；没有每批累计全量序列化或 PG 大 JSON 更新  |
| 同一批次、文件登记、归档页回包丢失后重试          | 不重复文字、工具结果、Step、引用或助手 Message，revision 不多增                   |
| 每个可靠边界前后重启 actor                        | 已提交内容可重读；原 Run／Step 身份不变；未知模型结果不重放；副作用工具不盲目重跑 |
| 大工具结果或原生项超过 2 MB，整个 Run 超过 32 MiB | 本地保存和内部归档按块／页完成；列表无需读取大结果正文                            |
| 窗口滑动、结果清理、文件清理后重启                | 使用新 epoch 继续；公开历史仍完整；活动文本检索仍能找到已滑出内容                 |
| 两台设备、断线、乱序、revision 缺口               | RPC 补读与事件来自一致提交位置；输入、输出、运行状态不拼成不同版本                |
| 取消与结果取得／封存／PG 归档交错                 | 只有一个最终版本；符合完成与停止裁决；没有两个 revision 分配者                    |
| PG 已提交终态，DO 确认或 hub 通知丢失             | 只补确认和通知，不重执行；新一轮可在 PG 最终事务后受理                            |
| 删除与结果、文件登记、分页归档交错                | 不复活对话；正文和引用最终清理；没有持 PG 锁等待 DO 的死锁                        |
| 任务超过临时上传保留期，或 PG 引用登记暂时失败    | 所需文件受到 PG 引用保护；恢复优先完成已存结果，无副作用重放                      |
| 重复 Start／Retry、模型切换                       | 新归档可读；用户消息不重复；每 Turn 只显示最新尝试；原文参数不被重排              |

测量指标包括：逻辑新增／重写字节、DO 行读写、PG 写入与锁等待、提交 p50／p95、控制命令延迟、归档吞吐和时间、峰值内存、活动检索扇出。100 次每次新增 20 KB 的结果，单份正文最终约 2 MB；重复全量写逻辑累计约 101 MB，追加约 2 MB。公开与私有数据可能各保存一份，窗口重建和归档也有额外开销；该例不代表实际磁盘、WAL、网络或账单量。

已完成共用提交、DO 执行与恢复、PG 归档、控制命令、文件生命周期和所有正文读取入口。验证使用真实 SQLite 与 PostgreSQL，模型、R2、邮件和宿主接口仍使用测试替身；生产迁移与部署随后于 2026-09-30 完成。新增测试覆盖批次重放冲突、固定版本读取、工具登记／发出／结果、文件登记失败后的结果恢复、原生项追加与 epoch 切换、取消单一版本写入、长工具结果省略、窗口规划后读取、归档最终事务失败及页确认丢失。

100 次流增量实测：每次 12,000 个 UTF-16 码元（`中😀` 重复 4,000 次），最终 1,200,000 码元、UTF-8 2,800,000 字节；正文累计新增写入恰好 2,800,000 字节，未重写先前正文。此数字是测试记录的逻辑正文量，不是实际磁盘、WAL、费用或端到端性能基准。

公开全文接口与浏览器仍有大正文的内存／渲染成本；活动检索要访问用户的活跃 Run；当前请求仍持有必要的原生工作窗口。未测量线上 p50／p95、峰值内存、控制延迟和归档吞吐，已完成真实 Cloudflare 部署，但未做生产登录后的真实执行或故障切换测试。验收证据与未完成事项统一维护在 [system-review.md](system-review.md)。

可复跑：`pnpm --filter @heveta/server test`、`pnpm test:integration`、`pnpm --filter @heveta/server test:storage`。最后一项使用 Workerd 的原生 DO SQLite，销毁并重建运行时，验证文本块、固定旧版本、公开 revision 和私有加密原生项继续存在；PG 控制读取在此测试中使用替身。
