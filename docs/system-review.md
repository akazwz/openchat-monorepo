## 1. 异步工作必须属于发起它的登录实例

**约定**：`SessionOwner = userId + sessionVersion`，在操作开始时捕获；异步准备完成、提交副作用、接收结果时不能重新借用另一个会话的身份。

| 问题与触发                            | 原影响与证据                                                                                                 | 处理与状态                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 选择头像后，图片解码期间切换账号      | 解码完成才由 RPC 拦截器读取当前账号，会向新账号提交原账号选的头像；此前浏览器复现过请求头变成新账号          | `settings/avatar.ts` 接收文件选择时的 owner，发 RPC 前核对；过期结果不提示成功/失败。本轮本地验证                |
| 会话确认未完成时发生新的登录          | 旧 `GetCurrentUser` 成功、空结果或未认证错误会重新采纳旧账号/退出新账号；全局 promise 还会让新会话加入旧请求 | `auth/session.ts` 按 owner 合并确认，只采纳当前 owner 的响应；旧 promise 的 finally 不能清除新请求。本轮本地验证 |
| 退出或普通 RPC 的迟到响应跨越登录切换 | 旧退出清空新登录；旧 RPC 的未认证错误触发新会话的确认                                                        | 退出也核对 owner；RPC 成功/失败路径统一丢弃过期响应。本轮本地验证                                                |

相关路径检查：草稿上传、发送确认、运行快照、事件回调已有 owner 检查，保留其职责。新测试同时覆盖切到另一账号和同账号重新登录，不只比较 userId。

验证：`test/session-ownership.test.ts`、`test/auth-interceptor.test.ts`，可控延迟头像预处理、会话响应、退出响应和 RPC 响应。

**约定**：完整记录按服务端 revision 合并；临时显示值来自该资源最新一次操作；不携带快照的通知/空响应只触发补读，不能臆造当前服务端数据。

| 问题与触发                                   | 原影响与证据                                                                                          | 处理与状态                                                                                                      |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 资料/标题的旧事件迟到、删除后的旧读取返回    | 资料/标题回退、已删对话重新出现                                                                       | 服务端 revision、客户端单调合并及删除 ID 墓碑。此前已部署，本轮既有测试再验证                                   |
| 初次读取记忆尚未完成时收到变更通知           | 直接 invalidate 会加入旧请求，没有再读取变更后的列表                                                  | `lib/refresh-queries.ts` 先取消旧读取，再 invalidate；记忆事件和重连共用。本轮本地验证                          |
| 清空记忆已提交，但命令响应晚于新增记忆的补读 | `onSuccess` 无条件写 `[]`，把服务端仍存在的新记忆从界面擦掉                                           | `settings/memory-commands.ts` 统一删除/清空后的重新读取；pending 删除仍是显示层覆盖，不写虚构快照。本轮本地验证 |
| 连续两次改名，后一次先成功、前一次仍 pending | 浏览器确认底层 store 为 `Rename_Second`，页面却显示 `Rename_First`；只过滤 pending 导致旧意图重新出现 | `lib/optimistic-values.ts` 先选每个资源的最后一次意图，再判断 pending；用户名和对话改名共用。本轮本地验证       |

## 扩查覆盖与验证结果

- 入口与身份：RPC 公共方法/认证拦截器、账号归属、邮箱验证码、会话确认/退出、头像准备/存储/回收。
- 对话与命令：列表及消息分页、搜索/改名/删除、草稿移交、上传取消、StartTurn 幂等、RetryTurn 最新尝试约束、CancelRun 撤回、任务接受与 Actor 唤醒。
- 同步与存储：单用户事件通道、心跳/重连、版本断档恢复、运行提交/快照锁、外键所有权、引用附件保留和垃圾回收、记忆事件与命令响应。
- UI：首页/对话/设置切换、长内容窄屏布局、加载/失败/恢复、两类编辑弹窗。
- 前端 46 项测试通过；服务端 40 项单元测试通过；独立 PostgreSQL 容器的 44 项集成测试通过。
- web 类型检查、lint、主题产物一致性检查及生产构建通过。

## 限制与设计取舍

- 浏览器故障注入使用本地受控 RPC 和 WebSocket，不修改生产账号；触摸为模拟，真机软键盘及真实 Cloudflare 多实例时序未重新实测。
- PostgreSQL 集成测试使用真实数据库，云端对象存储、模型及部分宿主接口使用测试替身。运行时模型/第三方工具内部不是本轮逐行复审范围。
- 普通资源通知仍是尽力投递，通过下次读取/重连收敛；运行终态由 Actor 持续重投直到成功。本轮未把通知系统改成持久事件日志。
- 共享主题的长文本规则也被站点使用，已进行共享包/应用类型与构建检查；没有逐页重新审查营销站。
- 这些结果是上述范围的已确认闭环，不表示所有实现或所有时序都已穷尽。

### P1 实施与验证记录（2026-09-29）

- **根因与证据：** `runs/driver.ts` 定时复制累计 parts，`runs/commit.ts` 读取旧 parts、比较后写回完整数组；操作边界保存变化后的整份 `LoopCheckpoint.messages`。输出增加时累计写入量持续放大；不能只迁私有 checkpoint 而保留公开消息全量更新。
- **定义与修复边界：** 保留 Thread → Turn → Run → Step；新增工具 PENDING 与调用前 RUNNING，分别记录 createdAt／startedAt；片段元数据保存 stepIndex；步骤边界变化统一为 StepUpdate；窗口计数统一为 omitted.contextSegments。重启不创建新 Run 或 Step；未知模型结果与未知副作用仍不重放。
- **实现：** RunActor SQLite 分块暂存与提交增量、固定 commitSeq 的片段版本、原生工作窗口追加及 epoch 重建；冻结 seal 后按分页摘要幂等归档 PG，最终事务才发布终态和释放 Thread。GetRun、重复请求、消息列表、工具结果详情及 conversation_search/read 接通活动与归档来源；长结果在读取正文前省略，下一轮窗口先规划再读正文。取消意图仅写 PG，公开 revision 仅由 DO 分配；文件结果先可靠保存，再登记 PG 引用。按用户确认的绿地开发移除旧 PG checkpoint 与累计写入入口，无旧历史兼容或双轨存储。

- **做法要点**：不新增 Run 状态，等待的是一次工具调用（Step PENDING + `consent`）；loop 以 WAITING 返回、driver 不写终态、actor 取消闹钟休眠；答复由 actor 以一次普通提交写进 checkpoint 和对话里的调用，再唤醒。

- **验证限制**：集成测试不模拟 Durable Object，actor 里的竞态处理（`cancel` 的二次唤醒、收尾时重新判断是否休眠）只按代码推演；真实环境的“同意后发信”、长时间等待后恢复、多设备同时答复没有实测。

### 待验证疑点

- 读取路径的查询次数：定稿回复每条 2 次片段元数据查询，再加每个带正文的 part 一次，按 part 顺序执行（`threads/content-store.ts`）；`ListMessages` 一页 50 条并行跑在 5 个连接上（`threads/service.ts:259-275`），`GetRun`、终态发布同路径。工具调用多的对话一页是几百到上千次往返。按代码计数，未实测耗时。
- 远程控制锁可能被自己的旧会话占住约两小时（`devices/connection.ts:258-265` 等）：释放依赖服务端先 `close()` 后 `webSocketClose` 仍被回调，workerd 行为未实测。
- 服务端没有主机心跳超时：ping 由自动应答处理，Mac 合盖不发 FIN 时 `online` 保持多久取决于 Cloudflare 何时判定连接已死。
- `host()` 依赖旧 socket 被 `close(4000)` 后 `readyState` 立即不再是 OPEN（`devices/connection.ts:62-66`）。
- 含 U+0000 的 ID、`challenge`、游标、上传文件名直接进 text 参数，应得 22021 并映射为 Internal；`ListComputerFiles` 指向文件、`GET /computer-file` 指向目录或空路径也答 500（子审查报告，主线程未逐条复核）。

### 设计取舍观察

- Run 的 actor 在输入校验之前就布防（`turns/service.ts:28-33`）：每个被拒或重放的提交都留下一个 60 秒后醒来、开一次数据库连接再自毁的对象。
- 同一网络在冷却期内对同一邮箱再发码，拿到的是同一个 challenge（`auth/service.ts:134-148`），知道邮箱的同网络用户可以耗掉它的 5 次猜测；`NOT_INVITED` 让外部能区分“有账号或已受邀”与“都不是”。
- 日程没有变更事件，活动页靠挂载和聚焦时补读。
- `/workspace` 的限制是词法检查，其中指向外部的符号链接可被读写（容器整个属于该用户，不算越权）；文件列表不显示符号链接。
- `StartRemoteDesktop` 先取 TURN 凭证再问设备状态，TURN 不可用时离线设备得到 Unavailable 而不是 `DEVICE_OFFLINE`。
- `ListMessages` 遇到读不到的活动 Run 整页失败，不返回缺正文的消息（run-storage.md 的约定）。
